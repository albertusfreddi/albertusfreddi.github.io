Deploying Lightweight FastAPI Microservices with Docker Swarm on Local Cloud

16 min read • 2026-10-05

Production context: A logistics startup in Jakarta was running eight backend services across three small VPS instances, with no load balancer and deploys done by hand over SSH. We consolidated them onto one Docker Swarm cluster on a $40/month local cloud node pool, added Traefik for routing and auto-TLS, and got to zero-downtime rolling deploys without touching Kubernetes. Deployment time fell from 40 minutes of manual steps to a single docker stack deploy, and the team stopped paying for idle resources it was not using.

Kubernetes Is the Right Tool for a Problem Most Startups Do Not Have

Kubernetes solves a real problem: running thousands of workloads across hundreds of nodes, with fine-grained scheduling, policy, and multi-tenancy. It is also, by any honest accounting, heavy. The control plane alone wants at least three nodes, etcd is its own operational discipline, and the object model is deep enough that a small team spends weeks learning what a Deployment, a ReplicaSet, and a StatefulSet each actually do before shipping anything.

The key insight is that orchestration need scales with the number of distinct concerns in your system, not with some number of microservices you read in a blog post. Eight services, one database, one queue, a couple of background workers, and one operator is not a Kubernetes problem. It is a Swarm problem, and Swarm is designed exactly for that band.

Why Docker Swarm, Specifically

Swarm's value is not that it is powerful. It is that it is proportionate. It reuses the Docker concepts a team already knows, images and networks and volumes, and adds only a few: a service (a desired state of N replicas), a stack (a YAML file describing many services), and an overlay network that lets containers talk across hosts. That is nearly the entire API surface a small team has to hold in its head.

The second reason is operational. Swarm does not need a separate control plane you babysit; the manager role runs on one of your existing nodes, with replicas elected automatically. For an eight-service system, a three-manager setup is the whole of the "platform," and it degrades gracefully to a two-manager quorum during maintenance. Compare that with standing up etcd, a scheduler, an API server, and a controller-manager, each with its own logs and its own way of failing.

docker-stack.yml — the entire top-level description of the system
version: "3.8"

services:
  api:
    image: registry.example.id/logistics-api:2.4.0
    deploy:
      replicas: 4
      update_config:
        parallelism: 1
        order: start-first
        failure_action: rollback
      restart_policy:
        condition: on-failure
    networks:
      - overlay

  worker:
    image: registry.example.id/logistics-worker:2.4.0
    deploy:
      replicas: 2
      restart_policy:
        condition: any
    networks:
      - overlay

  traefik:
    image: traefik:v2.11
    command:
      - "--providers.docker.swarmMode=true"
      - "--providers.docker.exposedByDefault=false"
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock:ro
    deploy:
      placement:
        constraints:
          - node.role == manager
    networks:
      - overlay

networks:
  overlay:
    driver: overlay

Notice what is not here: no pod specs, no service accounts, no resource quotas, no namespaces. That is the whole point. The file describes the actual system this business runs, nothing more, and anyone on the team can read it end to end in a minute.

Routing and TLS with Traefik, Not a Hand-Rolled Nginx

The most common mistake we see in small deployments is hand-maintaining an Nginx config that maps hostnames to upstream IPs. The moment replicas move or an IP changes, that config lies to you, and the outage comes from the one piece that was supposed to look simple. Traefik's Swarm provider reads the Docker API directly: it discovers healthy replicas automatically and loads routing rules from labels on the service itself.

labels on the api service — routing declared next to the app
  api:
    image: registry.example.id/logistics-api:2.4.0
    deploy:
      labels:
        - "traefik.enable=true"
        - "traefik.http.routers.api.rule=Host(`api.logistik.id`)"
        - "traefik.http.routers.api.tls.certresolver=letsencrypt"
        - "traefik.http.services.api.loadbalancer.healthcheck.path=/healthz"
      replicas: 4
      restart_policy:
        condition: on-failure

(In a real stack YAML the host rule is written as Host(`api.logistik.id`); unknown hosts are shown conceptually above to stay clear of a code fence.) The health-check path feeds Traefik's load balancer, so a replica that starts returning 500s is drained from the pool automatically instead of taking a share of production traffic. That single label is worth more than any static upstream list, because it can never drift from the service it describes.

The FastAPI Side: Stateless, Health-Checked, and Horizontal

For microservices to actually scale horizontally, they have to obey one rule: a request can land on any replica and produce the same result. That means no in-memory session that is not also shared, no server-local file the next request depends on, and no state in the process that matters beyond a single request. FastAPI makes this easy to enforce because the framework keeps things explicit: dependencies are wired per-request, and anything with a lifecycle goes through a lifespan context.

main.py — a resilient, health-checked service entry point
from contextlib import asynccontextmanager
from fastapi import FastAPI

@asynccontextmanager
async def lifespan(app: FastAPI):
    # Open shared connections (Postgres pool, message client) here.
    app.state.pool = await create_pool()
    yield
    await app.state.pool.close()

app = FastAPI(lifespan=lifespan)

@app.get("/healthz")
async def healthz():
    # Liveness: process is up. Readiness checks a dependency below.
    return {"status": "ok"}

@app.get("/readyz")
async def readyz():
    # Readiness: can this replica actually serve?
    db_ok = await ping_database(app.state.pool)
    if not db_ok:
        return JSONResponse({"status": "unready"}, status_code=503)
    return {"status": "ready"}

The split between /healthz and /readyz is not pedantry. Liveness tells Docker whether to restart the container; readiness tells the load balancer whether to send it traffic. If the database is down and you only have liveness, every replica gets restarted in a loop while the real problem, the database, goes nowhere. With readiness, the replicas stay running, stop accepting traffic, and the outage is isolated until the dependency recovers.

Rolling Deploys That Do Not Drop a Request

The whole reason to bother with orchestration at all is to deploy without dropping traffic. Swarm's update_config gives you three levers that, together, make a rolling deploy safe: parallelism controls how many replicas change at once, order: start-first means the new container starts and passes its health check before the old one stops, and failure_action: rollback means a failed deploy puts you back where you started instead of leaving you in a half-upgraded state.

deploy script — build once, promote by digest
#!/usr/bin/env bash
set -euo pipefail

SERVICE="$1"
TAG="$2"
REGISTRY="registry.example.id"

# Build once and tag immutably, so the deploy promotes an exact digest.
docker build -t "$REGISTRY/$SERVICE:$TAG" "./services/$SERVICE"
docker push "$REGISTRY/$SERVICE:$TAG"

# Update only that service inside the running stack.
docker service update "$SERVICE" \
  --image "$REGISTRY/$SERVICE:$TAG" \
  --update-parallelism 1 \
  --update-order start-first \
  --update-failure-action rollback \
  --with-registry-auth

Two habits matter here. First, you build and push a uniquely tagged image, then promote that exact image into the stack; you never rely on a mutable latest tag, because "latest" on Monday is not "latest" on Tuesday and rollbacks need an exact target. Second, the deploy updates one service, not the whole stack, which keeps the blast radius to the thing you actually changed and makes the rollback trivial.

Layout: Teaching Swarm Where Things Should Run

In a cluster as small as three nodes you might not need placement constraints at all, but there are two things worth pinning. The manager role is best kept off the hottest worker traffic, and stateful things (the database, the queue) should have restart and update behaviour that does not assume they are disposable the way the stateless API is.

WorkloadReplicasRestart policyPlacement constraint
API (stateless)4on-failureany worker
Worker (background)2anyany worker
PostgreSQL1any + mountpin to the node holding the volume
Traefik1anynode.role == manager

The database is the one row that demands care. In Swarm you pin stateful services to the node that owns their named volume, because a database container that floats between nodes while its data stays behind is a staged disaster. When you grow past one node, that is the signal to move the database to a managed service or a dedicated host, not to fight Swarm's scheduler with ever more creative constraints.

Failure Modes We Actually Hit

Failure modeSymptomFix
Only a liveness probe, no readinessRestart loop during a database outage, every replica flappingAdd /readyz and point the LB health check at it
Mutable latest tagRollback promoted the wrong imageImmutable versioned tags, promote by digest
Stateful DB left un-pinnedDB container rescheduled, data left on the old nodePin to the volume's node, or move DB off the swarm
Update with order: stop-firstBrief 503s during every deploySwitch to start-first so new pod is healthy first

Each of those was a mistake we made in production and each has the same shape: the failure came from leaving a default in place that assumed the wrong thing. Liveness assumes the process being up means it can serve; latest assumes a tag is stable; an un-pinned volume assumes storage follows the container. The discipline of orchestration is mostly the discipline of not leaving an assumption unchecked, and Swarm surfaces those assumptions clearly enough that a small team can actually keep up with them.

When Swarm Stops Being Enough

Swarm is the right answer for the band where you have a handful of services, a handful of nodes, and one team owning it all. The honest triggers for moving to Kubernetes are not "we read that it is the industry standard." They are things like: you need GitOps and policy that a multi-team organisation requires; you need autoscaling that refuses to be approximated with manual replica counts; you need hundreds of nodes and the scheduler has to make placement decisions a human simply cannot. Until one of those is true, Swarm will carry you further than its reputation suggests, and the money and attention you save can go into the application, which is where the actual business lives.
