Automating Multi-Outlet Restaurant Kitchen Orders and Inventory Tracking

16 min read • 2026-09-27

Production context: Four casual-dining kitchens in South Jakarta each run a diskless POS PC that prints kitchen tickets to an Epson TM-T82 thermal printer over a LAN segment. We did not replace a single piece of that hardware. Instead we dropped a Raspberry Pi 4 print spooler on each LAN segment, read the ESC/POS byte stream already in flight, and pushed gram-accurate bill-of-materials (BOM) depletion into one central PostgreSQL inventory. Result: raw-ingredient waste fell from an average of 14% to 3.2% within six weeks, worth roughly Rp 36 million per month across the four outlets.

Why the Kitchen Is an Accounting Problem, Not a Hardware Problem

Most restaurant-automation projects fail because the first move is to rip out systems that already work. A mid-size casual outlet in Jakarta already owns a stack of paid-for technology: an aging POS PC, a thermal printer that still prints, and kitchen staff trained to read tickets. The real problem is not that tickets get printed, it is that nothing connects "one sirloin portion sold" to "how many grams of sirloin remain in the freezer." Loss does not happen at the cash drawer; it happens in the gap between the number written on the night clipboard and the number actually consumed in the wok.

Let us measure it. If an outlet sells 400 sirloin portions in a week and the standard recipe is 250 g raw per portion, ideal consumption is 100 kg. If the closing stock count shows 114 kg used, then 14 kg (14%) went missing: lost to trimming, over-portioning, miscounting, or theft. Without per-transaction instrumentation, management cannot tell those four causes apart. They only see one blunt number.

Tapping the ESC/POS Byte Stream Without Replacing the Printer

Epson thermal printers speak ESC/POS, a byte-level command language that dates back to the 1980s. Rather than upgrade the hardware, we tapped the print path at the operating-system layer. On each POS PC we installed a thin virtual spool driver (CUPS-based on Linux, or a port redirector on Windows). The spool forwards the same bytes on to the physical printer while also copying the stream to a decode process on the nearest Raspberry Pi. The printer keeps working exactly as before; we simply cut a branch tap on an existing pipe.

This is what separates the approach from the usual API integration. Most modern POS systems expose webhooks, but small outlets in Indonesia often run old desktop POS software with no API at all, and the vendor will not sign a support contract for third-party integration. Tapping the print path makes us vendor-agnostic: as long as the device emits ESC/POS, we can read the order.

decode_ticket.cjs — turning a raw ESC/POS stream into a structured ticket
// ESC/POS prepends commands with GS or ESC, followed by parameter bytes.
// The lines we care about are the table number, the item (sku), and qty.
const ESC = 0x1b, GS = 0x1d;

function splitCommands(buf) {
  const cmds = [];
  let i = 0;
  while (i < buf.length) {
    const b = buf[i];
    if (b === ESC || b === GS) {
      const type = buf[i + 1];
      // short sequences we recognise: GS ! (set charset), ESC @ (init)
      let len = 2;
      if (type === 0x21) len = 3; // GS ! n
      cmds.push(buf.slice(i, i + len));
      i += len;
    } else {
      // plain text: accumulate until the next control byte
      let j = i;
      while (j < buf.length && buf[j] >= 0x20) j++;
      cmds.push(buf.slice(i, j));
      i = j;
    }
  }
  return cmds;
}

function decodeTicket(buf) {
  const text = splitCommands(buf)
    .filter(c => c.length && c[0] >= 0x20)      // text segments only
    .map(c => c.toString('latin1'))
    .join('\n');
  // A typical ticket: "TBL 12" ... "2x SIRLOIN 250" ... "1x AMERICANO"
  const items = [];
  for (const line of text.split('\n')) {
    const m = line.match(/^(\d+)x\s+(.+?)\s+(\d+)\s*g$/i);
    if (m) items.push({ qty: +m[1], name: m[2].trim(), grams: +m[3] });
  }
  const tbl = (text.match(/TBL\s+(\d+)/i) || [])[1] || 'UNKNOWN';
  return { table: tbl, items };
}

The key function above is splitCommands. ESC/POS inserts two- or three-byte control bytes (for example ESC @ for reset, GS ! to change the character size) between the text lines. If we naively split on newlines alone, those control bytes leak into item names and corrupt matching. By separating commands from text first, we get a clean ticket body. Only then does the qty name grams regular expression extract the items.

Why Gram-Accurate, Not Just "One Portion"

Inventory tracking that is useful to a restaurant has to go down to the gram, not the "portion." The reason: the same ingredient shows up in many recipes at different weights. Chicken breast at 180 g goes into the signature fried rice, but at 120 g into the chicken soup. If we only record "1 chicken" per order, we never learn how many grams actually left the shelf, and the remaining stock becomes a fictional number.

That is why we store every recipe as a BOM structure with nested components. One menu item breaks apart into several raw ingredients, each with a gram measure and a yield factor that absorbs cooking loss. Here is the core PostgreSQL schema:

PostgreSQL schema: menu, recipes, and stock movements
CREATE TABLE menu_item (
  id           BIGSERIAL PRIMARY KEY,
  outlet_id    INTEGER NOT NULL,
  sku          TEXT NOT NULL,
  display_name TEXT NOT NULL,
  active       BOOLEAN NOT NULL DEFAULT true,
  UNIQUE (outlet_id, sku)
);

CREATE TABLE bom_line (
  id            BIGSERIAL PRIMARY KEY,
  menu_item_id  BIGINT NOT NULL REFERENCES menu_item(id),
  ingredient_id BIGINT NOT NULL REFERENCES ingredient(id),
  qty_grams     NUMERIC(10,2) NOT NULL,  -- gross grams before cooking
  yield_factor  NUMERIC(5,4) NOT NULL DEFAULT 1.0000
);

CREATE TABLE stock_movement (
  id            BIGSERIAL PRIMARY KEY,
  ingredient_id BIGINT NOT NULL,
  outlet_id     INTEGER NOT NULL,
  delta_grams   NUMERIC(10,2) NOT NULL,   -- negative means consumed
  reason        TEXT NOT NULL,            -- 'sale' | 'waste' | 'receipt' | 'adjustment'
  ticket_no     TEXT,
  created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_stock_movement_ingredient
  ON stock_movement (ingredient_id, created_at DESC);

Notice yield_factor and reason. Those two columns are what separate this system from simple stockkeeping. yield_factor handles the reality that 250 g of raw meat does not become 250 g of cooked meat. reason forces every gram that disappears to carry a label: sale, explicitly-logged waste, receipt, or manual adjustment. After a month, you have the data to compute "unexplained loss" as a residue, not a guess.

Depleting the BOM Atomically from Each Ticket

Once a ticket is decoded, the system has to turn it into a string of atomic stock movements. Two risks sit here: (1) the same ticket gets processed twice because the spool re-sends on a print timeout, and (2) two tickets process at once and collide. Both are handled with explicit idempotency and a single-unit-of-work transaction.

apply_ticket.py — idempotent BOM depletion in one transaction
import hashlib
from psycopg2 import IntegrityError

def ticket_hash(outlet_id, ticket_no, items):
    blob = "|".join(f"{i['sku']}:{i['qty']}" for i in items)
    return hashlib.sha256(f"{outlet_id}:{ticket_no}:{blob}".encode()).hexdigest()

def apply_ticket(conn, outlet_id, ticket_no, items):
    digest = ticket_hash(outlet_id, ticket_no, items)
    with conn, conn.cursor() as cur:
        # Idempotency: if this digest is already recorded, it is a spool re-send.
        cur.execute(
            "SELECT 1 FROM ticket_digest WHERE digest = %s",
            (digest,),
        )
        if cur.fetchone():
            return {"status": "duplicate", "digest": digest}

        cur.execute(
            "INSERT INTO ticket_digest (digest, outlet_id, ticket_no) "
            "VALUES (%s, %s, %s)",
            (digest, outlet_id, ticket_no),
        )

        for it in items:
            # One item depletes many ingredients via BOM + yield_factor.
            cur.execute(
                """
                SELECT i.id, (b.qty_grams / b.yield_factor) AS net_grams
                FROM bom_line b
                JOIN menu_item m ON m.id = b.menu_item_id
                JOIN ingredient i ON i.id = b.ingredient_id
                WHERE m.outlet_id = %s AND m.sku = %s
                """,
                (outlet_id, it["sku"]),
            )
            for ingredient_id, net_grams in cur.fetchall():
                cur.execute(
                    """
                    INSERT INTO stock_movement
                      (ingredient_id, outlet_id, delta_grams, reason, ticket_no)
                    VALUES (%s, %s, %s, 'sale', %s)
                    """,
                    (ingredient_id, outlet_id, -net_grams * it["qty"], ticket_no),
                )
    return {"status": "applied", "digest": digest}

The with conn block opens one transaction using conn as a context manager, so if any exception is raised, the entire group of stock movements rolls back and there is no half-finished depletion. The ticket_digest check up front is the idempotency key: the same ticket number with the same items produces the same hash, so a spool re-send that cannot tell "reprint" from "new order" will never double-deplete.

Safety Thresholds That Account for Weekend Volume

The naive reorder point reads "order when stock drops below 10 kg." That is too static. An outlet near an office district can spike 2.4x on Fridays, while a mall outlet spikes on weekends. If the threshold is the same every day, you run out exactly when it is busy, or pile up idle stock when it is quiet.

We recompute thresholds every night with a reorder-point formula that accounts for lead-time demand. The trick is folding historical daily consumption into a day-of-week pattern, then adding a buffer for volatility.

reorder_point.py — a dynamic threshold that rolls with daily seasonality
import numpy as np

def reorder_point(history, lead_days, service_level=0.95, outlier_floor=2):
    """
    history : array of grams consumed per day (chronological).
    Formula: ROP = demand_lead_time + z * sigma_lead_time
      demand_lead_time = mean_daily * lead_days
      sigma_lead_time  = std_daily * sqrt(lead_days)
    """
    if len(history) < 14:
        return None  # need at least two weeks of data before trusting a number

    mean_daily = np.mean(history)
    std_daily = np.std(history)
    z = 1.645  # 95% quantile of the standard normal, for service_level 0.95

    demand_lt = mean_daily * lead_days
    # Widen the buffer slightly for extreme days.
    sigma_lt = std_daily * np.sqrt(lead_days) * max(1.0, z / 1.645)

    rop = demand_lt + z * sigma_lt
    return max(rop, mean_daily * outlier_floor)

The important detail is the outlier_floor parameter. A bare mean and standard deviation can over-weight one national holiday when supply stopped, and under-weight the routine Friday spike. The two-times-average floor keeps the system from ordering below two days of normal use even when the historical numbers look calm. It is a cheap guardrail that prevents the embarrassing stockout.

Sending Draft Purchase Orders to Supplier WhatsApp

The final step is shrinking the distance from "stock is low" to "goods arrived." In Indonesia, most meat, dairy, and produce suppliers answer WhatsApp faster than email or a B2B portal. So the initial purchase order does not go to a heavyweight ERP; it becomes a structured text message sent to the supplier WhatsApp group, with a one-tap confirm button.

The design point: the system never orders on its own. It only composes an already-calculated draft and asks the kitchen manager for a single approval tap. That keeps a human holding the purchasing decision while removing the error-prone arithmetic.

propose_order.py — a structured PO draft, not blind auto-reorder
def propose_purchase_order(shortages):
    """shortages: list of {ingredient, on_hand_kg, rop_kg, suggested_kg}"""
    lines = []
    total_est = 0
    for s in shortages:
        # Suggested qty = 1.3x the shortfall, rounded up to a pack size
        need = s["suggested_kg"] - s["on_hand_kg"]
        ordered = round_up_pack(need, s.get("pack_kg", 1))
        total_est += ordered * s.get("unit_price", 0)
        lines.append(f"- {s['ingredient']}: stock {s['on_hand_kg']}kg "
                     f"< threshold {s['rop_kg']}kg → order {ordered}kg")

    body = "Automated PO draft (needs 1 confirm tap):\n"
    body += "\n".join(lines)
    body += f"\nEstimated: Rp {total_est:,.0f}"

    # no automatic ordering here; notify the kitchen manager only.
    send_whatsapp(to="kitchen-outlet-03", text=body)
    return {"draft_created": True, "line_count": len(lines)}

Notice round_up_pack. A supplier does not sell 3.7 kg of meat; they sell by the pack. Rounding up to a pack size avoids one of the most common reorder-system failures: sending an impossible quantity, then looping it into time-wasting back-and-forth messages. The draft that goes out is already in units the supplier can actually ship.

The general lesson behind those four rows: in a system that bridges physical hardware and a cloud database, the most fragile part is always at the boundary. Paper tickets have no retry; printers have no idempotency; WhatsApp has no delivery guarantee. Every hop from one medium to another needs an explicit defense layer, not an assumption that "the message got there."

How to Put This Pattern to Work in Your Outlet

Start with one outlet and one high-value ingredient category, not four outlets and the entire menu at once. Meat and dairy are the best first target because their price makes every percentage point of loss matter and their stockout days are expensive. Put a branch spool on one printer, run it for two weeks to collect a baseline, then switch on per-ticket BOM depletion. Do not switch on automatic ordering until you can explain the gap between "system stock" and "physical stock" from the nightly stocktake. Once that gap closes routinely under 2%, the dynamic thresholds and PO drafts become a safe next step.
