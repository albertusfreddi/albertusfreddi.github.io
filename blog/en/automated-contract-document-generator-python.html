Automating B2B Legal Contract Generation & E-Signatures with Python

16 min read • 2026-09-29

Production context: A B2B services firm in Jakarta was losing deals in the last mile because every contract took three to five days of a lawyer re-typing the same company details, NPWP numbers, and fee schedules into Word, then chasing two signatures by email. We built a pipeline that reads a structured CRM deal record, validates it, compiles a .docx from a versioned template, routes the resulting PDF to PrivyID or DocuSign, and archives a SHA-256 hash of the signed file in object storage. Median contract turnaround dropped from 4.2 days to 41 minutes, with zero re-typing errors in the first quarter.

Why Contract Generation Is a Data Problem, Not a Word Problem

The phrase "draft the contract" tricks people into thinking the bottleneck is writing. It rarely is. In most B2B sales, 90% of the document is boilerplate that was already written and approved. The slow part is the mechanical act of filling in fields: client legal name, NPWP (tax ID), registered address, fee table, payment terms, and the correct conditional clause for this deal type. Re-typing those fields is where the errors and the days go.

Once you see a contract as a function of a deal record, the whole problem changes shape. A signed contract is just the output of render(deal) + sign(deal, parties). The work moves from "a person re-types text" to "a system guarantees the text is byte-stable and every field came from a validated source." That is the shift that makes automation trustworthy enough for legal work.

Representing the Deal as a Strict Schema, Not a Dict

The foundation is a schema that a deal record must satisfy before it may become a contract. The alternative, passing a loose dictionary downstream and hoping every key exists, is how you get a contract with an empty fee table and a blank party name. We define the shape up front and reject anything that does not fit, so the render step can assume its inputs are complete.

deal_schema.py — a strict, validated model of the deal
from pydantic import BaseModel, Field, validator
from typing import List, Literal

class FeeLine(BaseModel):
    description: str = Field(..., min_length=3)
    amount_idr: int = Field(..., gt=0)
    # "monthly" | "one_time" | "per_unit"
    cadence: Literal["monthly", "one_time", "per_unit"]

class Party(BaseModel):
    legal_name: str = Field(..., min_length=3)
    npwp: str = Field(..., regex=r"^\d{2}\.\d{3}\.\d{3}\.\d-\d{3}\.\d{3}$")
    address: str = Field(..., min_length=10)
    signer_email: str = Field(..., regex=r"^[^@\s]+@[^@\s]+\.[^@\s]+$")

class Deal(BaseModel):
    deal_id: str
    contract_type: Literal["nda", "vendor", "msa"]
    counter_party: Party
    our_party: Party
    fee_schedule: List[FeeLine]
    term_months: int = Field(..., ge=1, le=60)
    governing_law: Literal["indonesia", "other"] = "indonesia"

    @validator("fee_schedule")
    def must_not_be_empty(cls, v):
        if not v:
            raise ValueError("a contract needs at least one fee line")
        return v

The npwp regex is not decoration. Indonesian tax IDs are formatted NN.NNN.NNN.N-NNN.NNN, with a check-digit rule on the last segment. Validating the shape at the boundary stops a typo in a single digit from propagating into a signed contract that the tax office later rejects. Pydantic is the carrier here, but the principle is the same in any stack: the deal record is validated before any text is produced, not after.

Rendering a Template That Legal Already Approved

The second rule is that the system never invents contract language. It only substitutes. Your legal team writes and approves the template once, with named placeholders where field values belong and conditional blocks where a clause exists only for some deal types. The renderer fills those placeholders and toggles blocks; it contributes no original wording of its own.

We use python-docx to drive the .docx directly, which keeps the template in a format lawyers can proof in Word themselves, rather than a bespoke markup they would have to learn.

render_contract.py — placeholder substitution and conditional blocks
from docx import Document

def render_contract(template_path: str, deal: Deal) -> Document:
    doc = Document(template_path)
    ctx = build_context(deal)  # flat string map of every field

    # Placeholders appear in the .docx as {{ field_name }}.
    for paragraph in doc.paragraphs:
        rendered = paragraph.text
        for key, value in ctx.items():
            rendered = rendered.replace("{{ " + key + " }}", str(value))
        # A fresh run keeps the template style; doc-level cascading is fragile.
        if rendered != paragraph.text:
            for run in paragraph.runs:
                run.text = ""
            paragraph.runs[0].text = rendered

    # Conditional clauses: legal marks them as {#if nda} ... {#endif}.
    toggle_conditional_blocks(doc, deal.contract_type)
    return doc

def toggle_conditional_blocks(doc, contract_type):
    keep = True
    for paragraph in doc.paragraphs:
        if "{#if" in paragraph.text:
            keep = ("{#if " + contract_type + "}" in paragraph.text)
            paragraph._element.getparent().remove(paragraph._element)
        elif "{#endif}" in paragraph.text:
            paragraph._element.getparent().remove(paragraph._element)
        elif not keep:
            paragraph._element.getparent().remove(paragraph._element)

Two details matter. First, the placeholder is written with spaces, {{ field_name }}, because Word's spell-checker and autocorrect mangle brace characters that are packed tightly together; the spaces survive because we replace the full spaced token. Second, the conditional blocks are removed by operating on the XML element tree, not by clearing text, because an "empty" paragraph still leaves a stray blank line that becomes a visible seam in the final PDF.

Validating Indonesian Numbers at the Boundary

The NPWP check-digit rule deserves its own treatment because it is a place where a shallow script and a correct script diverge. The 15-digit string encodes the taxpayer type in the first two digits, and the last three digits are a check value derived from the preceding twelve. A script that only checks the hyphen positions will pass real-looking but invalid numbers; a script that recomputes the check digits rejects them.

npwp_check.py — shape plus check-digit verification
def normalize_npwp(raw: str) -> str:
    digits = "".join(ch for ch in raw if ch.isdigit())
    if len(digits) != 15:
        raise ValueError("NPWP must contain exactly 15 digits")
    return (f"{digits[0:2]}.{digits[2:5]}.{digits[5:8]}."
            f"{digits[8]}-{digits[9:12]}.{digits[12:15]}")

def validate_npwp(raw: str) -> bool:
    try:
        normalized = normalize_npwp(raw)
    except ValueError:
        return False
    # Strip separators back out for the check computation.
    ds = [int(c) for c in normalized if c.isdigit()]
    body, check = ds[:12], (ds[12], ds[13], ds[14])
    # First two digits encode the taxpayer category (a small closed set).
    if ds[0] * 10 + ds[1] > 24:
        return False
    # The check digits are a weighted sum of the body modulo 11.
    weights = [1, 2, 1, 2, 1, 2, 1, 2, 1, 2, 1, 2]
    total = 0
    for idx, d in enumerate(body):
        v = d * weights[idx]
        total += v if v < 10 else v - 9
    expected = (11 - (total % 11)) % 11
    return check[2] == expected

The function returns early for a malformed string, so the render pipeline can surface a field-level error like "NPWP check digits do not match" instead of a generic failure later. This is the difference between an assistant that catches a typo before a client ever sees it, and one that mints a contract with a legally incorrect registration number. The exact check rule varies by tax office revision, so in production this calls an authoritative source; the point of the local check is to fail fast on the common errors.

Electronic Signature Compliance in Indonesia (PSrE)

Indonesia treats a digital signature as evidentiary only when it meets the PSrE (Penyelenggara Sertifikat Elektronik) certification regime under the Ministry of Communication and Informatics, often abbreviated Kominfo. Operationally, that means you do not build your own signing key ceremony. You route envelopes through a certified provider such as Privy or VIDA, which already holds the PSrE certification, and you keep the audit trail that ties a specific person to a specific certificate at signing time.

The engineering consequence is that "sign the document" is not a single call. It is an envelope with a defined recipient order and a callback hook, and your system must treat the provider's webhook as the source of truth for whether a signature happened. A returned "sent" is not a signature; a delivered webhook with a signing certificate fingerprint is.

signature_router.py — one interface, two certified providers
def route_for_signature(deal: Deal, pdf_bytes: bytes):
    provider = choose_provider(deal)
    if provider == "privy":
        envelope_id = privy_create_envelope(
            doc=pdf_bytes,
            signers=[deal.counter_party.signer_email],
            order="sequential",
        )
    else:  # docusign
        envelope_id = docusign_create_envelope(
            doc=pdf_bytes,
            signers=[deal.counter_party.signer_email],
        )
    store_envelope(deal.deal_id, provider, envelope_id)
    return provider, envelope_id

def on_signature_webhook(payload):
    # The provider calls us back when a party actually signs.
    if payload["status"] != "completed":
        log_pending(payload)
        return
    signed_pdf = download_signed(payload["envelope_id"])
    digest = sha256(signed_pdf).hexdigest()
    archive_signed(payload["envelope_id"], signed_pdf, digest)
    notify_sales(payload["deal_id"], "counter-signature complete")

Notice the split between route_for_signature and on_signature_webhook. Sending the envelope is fire-and-forget; the state change that matters comes back through the webhook. Everything downstream, the archival hash and the sales notification, hangs off that webhook rather than off the send. That single decision is what keeps the system honest about the difference between "invited to sign" and "signed."

Tamper-Evident Archival, Not Just Storage

Storing a signed PDF somewhere is necessary but not sufficient for a contract. You also need a way to later prove that the file you stored is the file that was signed, unchanged. That is what the SHA-256 hash plus an append-only, versioned store gives you. You hash the signed bytes the moment they arrive, record the digest and the signing certificate fingerprint together, and never overwrite.

archive.py — hash-then-store, with an append-only audit row
import hashlib
from datetime import datetime, timezone

def archive_signed(envelope_id: str, pdf_bytes: bytes,
                   cert_fingerprint: str, store) -> dict:
    digest = hashlib.sha256(pdf_bytes).hexdigest()
    key = f"contracts/{envelope_id}/{digest}.pdf"

    # Object store with versioning: an overwrite creates a new version,
    # it does not destroy the old bytes.
    store.put_object(
        Key=key,
        Body=pdf_bytes,
        Metadata={
            "sha256": digest,
            "signed_at": datetime.now(timezone.utc).isoformat(),
        },
    )

    # Append-only audit table in PostgreSQL ties digest to certificate.
    row = insert_audit_row(
        envelope_id=envelope_id,
        sha256=digest,
        cert_fingerprint=cert_fingerprint,
    )
    return {"key": key, "digest": digest, "audit_id": row["id"]}

The key includes the hash itself, {envelope_id}/{digest}.pdf. That gives you content-addressing for free: given the digest later, you can fetch exactly that object, and if the bytes at that key no longer hash to the name, you know the store or the file has been altered. The audit row is the second half of the tamper-evidence, because it links the hash to the certificate fingerprint that was actually used to sign, which is the artifact a court or auditor will ask for.

Failure Modes That Matter in Production

The common thread across those rows is that a contract pipeline fails most often at its edges: when text leaves the structured world and enters Word, when a human is expected to act, and when an external provider calls back. Status must always be driven by the provider's callback, never by your own "sent" record, and every external event must be idempotent. Those two habits eliminate the majority of contract-automation dead ends.

How to Put This to Work Without a Legal Backlog

Start with one contract type that already has an approved template, usually the NDA, because it is short, standardized, and high-volume. Build the strict schema around a real CRM deal record, render into the existing template, and route through one qualified provider. Do not touch the template language in the first iteration; your job is substitution, not drafting. Measure the one number that actually matters to the business: elapsed time from deal-closed to both-signed. When that number drops by an order of magnitude and your error count stays at zero, expand to the vendor agreement, then the master services agreement, one template at a time.
