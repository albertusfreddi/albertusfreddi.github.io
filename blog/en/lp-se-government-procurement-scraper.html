Scraping Indonesian Government Procurement (LPSE): Architecture & Data Pipelines

16 min read • 2026-09-24

Production context: This is the tender-monitoring pipeline we operate for procurement vendors across Indonesia. It watches more than five hundred regional LPSE portals plus the central ones, extracts new tender notices and their Bill-of-Quantities attachments, and turns them into searchable, filterable records within minutes of publication. The constraints that shape the whole design: the portals run on a mix of SPSE 4.x builds with no shared API contract, many sit behind slow provincial infrastructure, and any one of them will silently start dropping or throttling our requests the moment we step over a polite crawl rate. The playbook below is the architecture we actually landed on.

Why LPSE Scraping Has No Single-Source Solution

The first mistake people make is treating lpse.go.id or the LKPP framework as one website. It is not. LPSE, the Layanan Pengadaan Secara Elektronik, is a national standard running on thousands of independently operated installations. Each province, each regency, and many ministries host their own portal, and each portal is an island with its own SPSE version, its own SSL configuration, its own schema quirks, and often its own uptime problems.

In practice we saw four distinct server generations in the wild at the same time: current SPSE 4.5 builds exposing the modern DataTables JSON endpoints, older 4.x builds with slightly different parameter names, a few installations where the SSL certificate had expired and the browser had to be told to proceed, and a handful that only rendered correctly with the text-based fallback endpoint. A crawler that assumed any one of these shapes would silently come back empty for every other.

This is why the very first architectural decision is to treat every portal as an untrusted, potentially broken, foreign system. No shared state, no shared assumptions, and a normalizer that accepts any shape and produces one. The rest of the design falls out of that.

Read the DataTables Endpoint Before You Write Any Crawler

Almost every modern SPSE portal renders its tender list through the server-side DataTables convention. The list API is a POST endpoint, usually /eproc4/dt/lelang, that returns a payload shaped like this:

Canonical DataTables response shape
{
  "draw": 1,
  "recordsTotal": 1432,
  "recordsFiltered": 1432,
  "data": [
    {
      "nama_paket": "Pengadaan Jaringan LAN",
      "kode_tender": "12345678",
      "pagu": "1.250.000.000",
      "satuan_kerja": "Dinas Komunikasi dan Informatika",
      "tanggal_pembuatan": "2026-09-20 09:41:00"
    }
  ]
}

Two details matter more than anything else. First, pagination is driven by start and length form fields, and you should always read recordsFiltered back rather than trusting an upfront count, because the server filters rows before it pages them. Second, the column ordering and the numeric formatting are localized: amounts arrive as strings with thousands separators and an Indonesian locale, so "1.250.000.000" must be parsed as a number and not fed straight into a decimal column. Resume safely by remembering the highest tender ID or timestamp you have already seen, and page forward from there only. That single habit is what lets a crashed crawler resume without re-reading 40,000 rows it already stored.

The Rate Limiter Is the Product

For a scraping pipeline, the polite-rate controller is not a feature bolted on at the end. It is the part that determines whether the system runs for a year or gets banned in a week. Government portals are heavily watched and often sit behind a WAF, so a burst of fifty requests from one IP in three seconds is both rude and self-defeating: it triggers a block that starves every other portal behind the same proxy.

We model one token bucket per portal domain. The bucket refills at a low, constant rate and lets a small burst through, then forces the worker to sleep when empty. The exact numbers live in a per-portal capacity table, because a fast ministry portal tolerates a higher rate than a regency server on a slow uplink.

Per-portal token bucket rate limiter
import asyncio
import time

class TokenBucket:
    def __init__(self, rate: float, burst: int):
        self.rate = rate            # tokens per second
        self.burst = float(burst)
        self.tokens = float(burst)
        self.updated = time.monotonic()

    async def acquire(self):
        while True:
            now = time.monotonic()
            self.tokens = min(self.burst,
                              self.tokens + (now - self.updated) * self.rate)
            self.updated = now
            if self.tokens >= 1:
                self.tokens -= 1
                return
            await asyncio.sleep((1 - self.tokens) / self.rate)

# one bucket per portal, held in a dict keyed by domain
buckets = {}

async def polite_get(domain: str) -> None:
    bucket = buckets.setdefault(domain, TokenBucket(rate=0.08, burst=2))
    await bucket.acquire()
    # now issue the request

Layering matters just as much as the rate. We wrap every request in exponential backoff with jitter, so that when a portal is genuinely slow, retries spread out instead of hammering the same second. A circuit breaker then tracks consecutive failures per domain and takes a portal out of rotation for a cool-down window when it has failed enough times in a row. The result is a crawl that degrades gracefully: one dead portal costs a little delay, never a cascade.

Retry with backoff and jitter around the DataTables call
import asyncio
import random
import httpx

async def fetch_page(client, domain, start, length):
    url = "https://" + domain + "/eproc4/dt/lelang"
    data = {"draw": 1, "start": start, "length": length}
    for attempt in range(4):
        try:
            resp = await client.post(url, data=data, timeout=20)
            resp.raise_for_status()
            payload = resp.json()
            return payload["data"], payload["recordsFiltered"]
        except (httpx.RequestError, httpx.HTTPStatusError):
            if attempt == 3:
                raise
            backoff = 2 ** attempt
            await asyncio.sleep(backoff + random.uniform(0, 0.5))

Session and TLS: The Two Things That Break First

Two failure classes account for most of the "why does my scraper return empty" confusion. The first is session state. Many SPSE installations require a cookie earned on a landing page before the DataTables endpoint will answer, and some set a CSRF-style token you must read from the rendered page and echo back as a form field. A session you never warm up looks identical to a portal that is down.

Warm a session and reuse the cookie jar across pages
async def build_session(domain):
    limits = httpx.Limits(max_connections=2, max_keepalive_connections=1)
    timeout = httpx.Timeout(30.0, connect=15.0)
    client = httpx.AsyncClient(limits=limits, timeout=timeout,
                               follow_redirects=True)
    landing = await client.get("https://" + domain + "/eproc4")
    landing.raise_for_status()
    return client

The second is TLS. A visible share of older portals run expired or self-signed certificates, and an out-of-the-box client refuses to connect. We do not disable verification globally; we maintain a small, explicit allow-list of domains whose certificate we have verified by hand and accepted, and for those domains only we point the transport at a purpose-built SSL context. Everything else keeps full verification. This keeps the door open for a broken-but-legitimate regency portal without silently trusting the entire internet.

Normalize Everything to One Record Shape

Because every portal is different, the worker that fetches a page should never be the one that decides what a tender is. Fetching returns raw rows; a separate normalizer maps raw rows into one schema. This separation is what lets us add a new portal, or fix one portal that changed its fields overnight, without touching the storage or alerting layers.

Normalizer maps any raw row into the canonical record
import re

def parse_idr(value):
    if value is None:
        return None
    digits = re.sub(r"[^d]", "", str(value))
    return int(digits) if digits else None

def normalize(source, raw):
    return {
        "source": source,
        "external_id": str(raw.get("kode_tender") or raw.get("id_tender") or "").strip(),
        "nama_paket": (raw.get("nama_paket") or "").strip(),
        "pagu": parse_idr(raw.get("pagu") or raw.get("nilai_pagu")),
        "hps": parse_idr(raw.get("nilai_hps") or raw.get("hps")),
        "instansi": (raw.get("satuan_kerja") or raw.get("instansi") or "").strip(),
        "published_at": raw.get("tanggal_pembuatan"),
    }

The key insight here is defensive access: use or chaining to accept several possible field names, never assume a field exists, and coerce everything to a primitive you can store and query. A row that lacks a field should produce a null, not a crash that takes down an entire worker.

Deduplication and Change Detection

A tender notice is not a stable object. The same package can reappear when a portal re-indexes, get a revised HPS value, or be retracted. If all you store is "saw this ID", every refresh looks like a new tender and the vendor drowns in duplicates. The fix is a fingerprint computed over the fields that actually matter, stored next to the row.

Content fingerprint separates true change from a re-fetch
import hashlib
import json

FIELDS = ("nama_paket", "pagu", "hps", "instansi", "published_at")

def fingerprint(record):
    canon = json.dumps({k: record.get(k) for k in FIELDS}, sort_keys=True)
    return hashlib.sha1(canon.encode("utf-8")).hexdigest()

On ingest the flow is: if the (source, external_id) pair is unknown, insert. If it is known but the fingerprint differs, update the row and mark it revised, so downstream alerts can flag a value change explicitly. If the fingerprint is identical, do nothing. This turns a noisy stream into a monotonic one and is the reason the system can run a full sweep every day without generating a mountain of false alerts.

PDF and BoQ: PyMuPDF First, OCR Only as a Fallback

The tender list gives you a package name and a ceiling amount. The Bill of Quantities, the document that lists every line item and quantity a bidder must price, lives in the attached PDFs. Some of those PDFs are born-digital and contain a text layer; many are scans with no text at all. Treating both the same way wastes either accuracy or money.

The rule is: extract the text layer first. Only when the result is suspiciously small do we fall back to OCR. This keeps the expensive, slow OCR pass reserved for the minority of documents that genuinely need it.

Text first, OCR only when the layer is empty or tiny
import fitz  # PyMuPDF

def extract_text(path):
    doc = fitz.open(path)
    text = "
".join(page.get_text() for page in doc)
    doc.close()
    if len(text.strip()) > 200:
        return text
    return ocr_fallback(path)

def ocr_fallback(path):
    import pytesseract
    from PIL import Image
    doc = fitz.open(path)
    chunks = []
    for page in doc:
        pix = page.get_pixmap(dpi=200)
        img = Image.frombytes("RGB", [pix.width, pix.height], pix.samples)
        chunks.append(pytesseract.image_to_string(img, lang="ind"))
    doc.close()
    return "
".join(chunks)

Note the Tesseract language pack set to ind, because Indonesian BoQ documents mix Indonesian and English terms and a default English model misreads common words. The BoQ text then feeds the same normalization pipeline as the list rows, getting parsed into line items with quantities, units, and prices where the document structure allows it.

The Storage Schema Must Answer the Buyers' Questions

The database is not an archive; it is a matching engine. A procurement vendor asks questions like "which open tenders in my KBLI classification and my province were published this week". The schema has to make those questions indexable instead of forcing a table scan.

Core tender table with the fields buyers filter on
CREATE TABLE tenders (
    id            BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    source        TEXT NOT NULL,
    external_id   TEXT NOT NULL,
    nama_paket    TEXT NOT NULL,
    pagu          NUMERIC(16,2),
    hps           NUMERIC(16,2),
    instansi      TEXT,
    klasifikasi   TEXT,
    wilayah       TEXT,
    published_at  TIMESTAMPTZ,
    first_seen    TIMESTAMPTZ NOT NULL DEFAULT now(),
    last_hash     TEXT NOT NULL,
    revised       BOOLEAN NOT NULL DEFAULT false,
    UNIQUE (source, external_id)
);

CREATE INDEX tenders_klasifikasi_idx
    ON tenders (klasifikasi, published_at DESC);
CREATE INDEX tenders_wilayah_idx
    ON tenders (wilayah, published_at DESC);

Two design notes: the numeric columns use NUMERIC(16,2) rather than a float because tender figures are money and must never accumulate floating-point error, and the natural key is the pair (source, external_id) rather than the external id alone, because id counters are per-portal and collide across portals. The uniqueness constraint is what makes the same dedup logic safe under concurrency.

Matching Tenders to Buyers and Pushing Alerts

Extraction is only half the job. The value is delivered as an alert: the moment a tender matching a vendor's classification appears, a structured message goes out with the package name, the ceiling, the deadline, and a link straight to the original portal. Matching runs against the classification and region fields, and the alert engine keeps a per-subscriber dedup key so it never pings the same person twice about the same unchanged tender.

Match new tenders against subscriber filters
def match_tender(tender, subscriptions):
    hits = []
    for sub in subscriptions:
        if tender["klasifikasi"] and sub["klasifikasi"] == tender["klasifikasi"]:
            if not sub["wilayah"] or sub["wilayah"] == tender["wilayah"]:
                hits.append(sub)
    return hits

The 48-hour advantage the vendors care about does not come from crawling faster than everyone else. It comes from the alert being structured and filterable immediately, so a sales team moves from "we found out late and guessed" to "we opened the correct BoQ the same morning". Speed without structure just moves the same confusion up the timeline.

Observe the Pipeline, Not Just the Scrapers

A pipeline that runs unattended across 500 portals needs a monitoring story that answers three questions without digging through logs: which portals are failing, how stale is the data, and did anything get stuck. We emit one metric per portal for last successful fetch, and one global gauge for the lag between a tender's publication time and our first sight of it.

Emit per-portal freshness and global lag
def record_result(domain, published_at, now):
    metrics.gauge("lpse.last_seen_epoch", now.timestamp(), {"portal": domain})
    if published_at:
        lag = (now - published_at).total_seconds()
        metrics.histogram("lpse.publish_lag_seconds", lag, {"portal": domain})

An alert fires when any portal has not been successfully fetched within its own cadence window, or when the global lag metric climbs, meaning we are falling behind real-time. This is what lets a one-person ops load handle 500 portals: you do not watch each portal, you watch the exceptions the metrics surface for you.

The Failure Modes You Will Meet

Here is the honest list of ways this system fails, and what we do about each.

FailureSymptomOur response
WAF or IP bansudden 403s or empty pages from one portalcircuit breaker removes the portal, alert on consecutive failures
Expired TLS certhandshake error on an old portalexplicit per-domain SSL allow-list
Schema driftnormalizer returns empty fieldsdefensive or access plus a schema-drift alert on empty external_id
Captcha pageHTML redirect with a challengetreat as a soft failure, back off, flag for manual review
Slow DBwrite latency climbs, queue backs upshard by source, batch inserts, keep an insert-only hot path

The philosophy throughout is the same: isolate the failure to one portal, keep it from cascading, and surface it as a named metric instead of a silent empty result. A scraper that reports "this portal is down" is maintainable; a scraper that quietly returns nothing is a time bomb.

What We Would Reuse and What We Would Not

If we built this again tomorrow, we would keep the strict fetch/normalize split, the per-portal token bucket, and the content fingerprint. Those three decisions carry the system. We would not hand-roll the orchestration again now that mature worker queues handle retries and scheduling out of the box, and we would not store BoQ text embedded in the main table, because attaching the parsed line items as a separate structure keeps the hot matching path fast. The durable lessons are boring and transferable: treat every remote system as broken until proven otherwise, make rate limits part of the core loop rather than an afterthought, and store only what a real question will filter on.
