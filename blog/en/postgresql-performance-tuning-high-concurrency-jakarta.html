PostgreSQL Optimization for 10M+ Row Tables Under Flash-Sale Concurrency

16 min read • 2026-10-22

Production context: This is the database layer for an Indonesian e-commerce marketplace that runs a flash sale every Friday at 18:00 WIB. The order table and the payment ledger each pass ten million rows, and checkout traffic spikes from a few hundred requests a second to several thousand in the first ninety seconds. The hard targets we hold to on sale night: checkout p95 under 120ms, database CPU under 15 percent, and zero deadlocks from inventory contention.

The Real Bottleneck Is a Hot Row, Not a Slow Query

Most people assume a flash sale kills the database because "the queries are too slow." That is rarely the first problem. The first problem is contention: a few hundred checkout requests all want the same inventory row at the same instant. Under PostgreSQL's MVCC, a SELECT ... FOR UPDATE takes a row lock, and every other transaction that touches the same row parks behind it in a queue that no index can save you from.

Here is the failure cascade we saw on the first sale, in order:

  • Lock queue forms: one request holds the row lock, forty others wait on it. Each waiting backend holds its own snapshot and its own memory.
  • Timeouts cascade: the default lock_timeout is zero, meaning "wait forever." Requests hang until the app-level HTTP timeout fires and the caller retries.
  • Connection exhaustion: because every hung request holds an open backend, max_connections gets eaten. New checkouts get "connection refused" or "sorry, too many clients already."
  • Deadlocks begin: two transactions each hold one row and want the other. PostgreSQL detects and aborts one, but the retried transaction re-enters the same queue.

The fix is not a bigger machine. The fix is to stop holding locks across round-trips and to stop treating a 10M-row append-only ledger like a small lookup table. The rest of this article is the playbook we actually applied, with the exact SQL.

Measure Before You Change Anything

Before touching a single setting, prove which connection is blocking which. Two queries do this. The first lists every backend currently waiting on a lock and how long it has been stuck:

Who is waiting on a lock
SELECT pid,
       usename,
       state,
       wait_event_type,
       wait_event,
       now() - state_change AS waiting_for
FROM pg_stat_activity
WHERE wait_event_type = 'Lock'
ORDER BY waiting_for DESC;

The second pairs each blocked process with the process that holds the lock, using the built-in pg_blocking_pids function. This is the one that tells you the exact culprit query:

Who is blocking whom
SELECT a.pid,
       a.query AS blocked_query,
       pg_blocking_pids(a.pid) AS blocked_by,
       b.query AS blocking_query
FROM pg_stat_activity a
LEFT JOIN pg_stat_activity b
  ON b.pid = (pg_blocking_pids(a.pid))[1]
WHERE cardinality(pg_blocking_pids(a.pid)) > 0;

On sale night we saw the same picture every time: dozens of SELECT ... FOR UPDATE on inventory, all blocked by one transaction that was itself waiting on an HTTP response. The lock was held not because the work was slow, but because the application held it open across a network hop.

Rule 1: Replace SELECT FOR UPDATE With a Conditional UPDATE

The most damaging pattern in a flash sale is this one, and it appears in almost every tutorial:

Anti-pattern: lock held across a round-trip
BEGIN;
SELECT stock FROM inventory WHERE product_id = 123 FOR UPDATE;  -- lock taken
-- ... app computes, calls another service, waits on HTTP ...
UPDATE inventory SET stock = stock - 1 WHERE product_id = 123;  -- lock finally freed
COMMIT;

Between the SELECT and the UPDATE, the row lock is held while the application does I/O it does not need to hold the lock for. That window is where the queue forms. The database can do the whole thing atomically in one statement, and the row lock is held only for microseconds:

Fix: one atomic statement, lock released immediately
UPDATE inventory
SET stock = stock - 1,
    reserved = reserved + 1,
    updated_at = now()
WHERE product_id = 123
  AND stock >= 1
RETURNING stock;

If the UPDATE returns zero rows, the seller is out of stock and you decline the order. No SELECT, no open transaction, no application-level lock hold. PostgreSQL guarantees the read-check-write is atomic, so two requests cannot both decrement the same unit of stock. This one change removed roughly ninety percent of the contention on inventory on the very next sale.

Two details make this safe. First, add lock_timeout as a session or role default so no request waits forever; a short timeout that fails fast is far better for a flash sale than a request that hangs:

Fail fast instead of hanging
ALTER ROLE checkout_app SET lock_timeout = '500ms';
ALTER ROLE checkout_app SET statement_timeout = '5s';

Second, if you genuinely need to read then write only for a subset of rows you are claiming and processing, use SKIP LOCKED rather than blocking.

Rule 2: Use SKIP LOCKED for Queues and the Outbox

The opposite pattern, where you do need to claim rows and process them, is a job queue or a transactional outbox. N workers all pick the next pending row. If they all do FOR UPDATE on the same row, they line up behind each other. SKIP LOCKED tells PostgreSQL: skip any row someone else has already locked and give me the next free one.

Claim one pending outbox row without blocking
WITH next_job AS (
  SELECT id
  FROM outbox
  WHERE status = 'pending'
  ORDER BY created_at
  FOR UPDATE SKIP LOCKED
  LIMIT 1
)
UPDATE outbox o
SET status = 'processing',
    started_at = now()
FROM next_job
WHERE o.id = next_job.id
RETURNING o.id, o.payload;

Each worker gets a different row and never waits on another worker. This turns a queue from a serialization point into a fan-out. The same tactic works for ledger reconciliation and for any "process this batch" job where workers must not double-claim.

Rule 3: Partition Ledgers Before They Hit 10M Rows

Contention is a write problem. Bloat is a different problem: the payment ledger and order audit tables grow by millions of rows a month, and a single table with a single B-tree index eventually stops fitting in memory. Queries still "work," but VACUUM takes longer, indexes spill to disk, and every constraint check touches more pages.

Declarative range partitioning splits the table by a time column. The application keeps writing to one logical table; PostgreSQL routes each row to the right partition.

Partition a ledger by month
CREATE TABLE payment_ledger (
  id bigint GENERATED ALWAYS AS IDENTITY,
  order_id bigint NOT NULL,
  amount numeric(15,2) NOT NULL,
  status text NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now()
) PARTITION BY RANGE (created_at);

CREATE TABLE payment_ledger_2026_10
  PARTITION OF payment_ledger
  FOR VALUES FROM ('2026-10-01') TO ('2026-11-01');

CREATE TABLE payment_ledger_2026_11
  PARTITION OF payment_ledger
  FOR VALUES FROM ('2026-11-01') TO ('2026-12-01');

Why it helps: a query filtered by created_at scans only the matching partitions (partition pruning), per-partition VACUUM runs faster and can keep up with writes, and you can drop or archive an old month with DROP TABLE payment_ledger_2025_06 instead of a long DELETE. Create partitions ahead of time with a monthly cron or a tool like pg_partman, and always keep a DEFAULT partition or a pipeline that catches the day the cron missed.

A caution: partitioning does not fix the hot-row problem from Rule 1. It is for append-only time-series style tables, not for a small inventory table that every request hammers.

Rule 4: Swap B-tree for BRIN on Append-Only Columns

On the same ledger tables, a B-tree index on created_at does two wasteful things: it stores a pointer for every single row, and it stores those pointers sorted across the entire table. For an append-only log where rows are physically written in time order, that is enormous and redundant. A BRIN (Block Range Index) stores one min/max pair per block range instead, which makes the index several hundred times smaller.

A BRIN index on a time-ordered column
CREATE INDEX payment_ledger_created_at_brin
  ON payment_ledger
  USING brin (created_at)
  WITH (pages_per_range = 32);

BRIN is fast for range scans over physically correlated data and cheap to maintain under heavy inserts. It is the right tool exactly when rows arrive roughly in order and you query by ranges of that column. Lower pages_per_range gives more precision at a slightly larger index; 32 is a good starting point for a monthly-partitioned ledger. The index footprint on our ledger dropped by 88 percent after the swap, and the small index stays resident in cache instead of thrashing disk.

Rule 5: Tune Autovacuum and Memory So the Table Stops Growing

PostgreSQL never overwrites a row in place under MVCC; an UPDATE writes a new version and leaves the old one as a dead tuple. Autovacuum is the background worker that removes those dead tuples. On a write-heavy e-commerce workload the default settings are too conservative, so dead tuples accumulate faster than they are cleaned, the table and its indexes bloat, and every query has to skip dead data.

These are the changes we applied, with the reasoning for each:

Autovacuum and memory tuning (postgresql.conf style)
autovacuum_vacuum_cost_delay = '2ms'   -- do more work per pass
autovacuum_vacuum_cost_limit = 2000      -- raise the work budget
autovacuum_naptime = '10s'               -- check more often
autovacuum_vacuum_scale_factor = 0.05    -- vacuum at 5% change, not 20%
autovacuum_analyze_scale_factor = 0.05

shared_buffers = '4GB'       -- about 25% of RAM; more than 8GB rarely helps
effective_cache_size = '12GB' -- a planner hint, not an allocation; ~75% of RAM
maintenance_work_mem = '1GB'  -- lets VACUUM and CREATE INDEX work in memory
work_mem = '8MB'              -- raise only if many sorts spill to disk
default_statistics_target = 200  -- better plans for skewed columns

The two that matter most here are autovacuum_vacuum_scale_factor and the cost limit. A 20 percent default means a 10M-row table only gets vacuumed after 2M rows change, by which point bloat is already visible. Dropping it to 5 percent keeps the dead-tuple count low. shared_buffers holds hot data in memory, but the value effective_cache_size is what the planner uses to decide whether an index scan beats a sequential scan, so set it to the realistic size of your working set, not the size of the buffer pool.

Two cautions. Do not raise autovacuum_vacuum_cost_delay to zero on a busy primary: autovacuum will compete with your live traffic for I/O. And do not blindly copy these numbers onto a tiny instance; they are proportions, not absolutes.

Rule 6: Stop Opening One Connection Per Request

Every PostgreSQL backend is a separate OS process with its own memory, so a spike that opens two thousand connections spends more time forking processes than running queries. The fix is a connection pooler in transaction mode in front of the database, with a small pool of real backends sized to roughly four times your vCPU count.

PgBouncer is the standard choice. The key setting is pool_mode = transaction: the pooler hands a backend to a client for the length of one transaction, then returns it. A burst of two thousand short checkout transactions then fans out against a pool of, say, forty backends, and queueing happens in the cheap pooler rather than in the database's process table.

PgBouncer essentials (pgbouncer.ini)
[databases]
shop = host=127.0.0.1 port=5432 dbname=shop

[pgbouncer]
pool_mode = transaction
default_pool_size = 40
max_client_conn = 4000
server_reset_query = DISCARD ALL

This works because none of the earlier fixes rely on a transaction spanning multiple statements. Once DISCARD ALL resets state between clients, a pooled backend is safe to reuse. Pair this with max_connections left at a sane number on PostgreSQL itself, and the "too many clients already" error stops appearing.

The fastest way to keep this from regressing is pg_stat_statements: enable the extension, then watch the top queries by time on sale night. If one query climbs the list, pull its plan with EXPLAIN (ANALYZE, BUFFERS) before you touch anything else.

Find the slowest statements in production
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;

SELECT query, calls, mean_exec_time, rows
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 10;

Everything above is reversible, observable, and tuned to a real workload rather than copied from a benchmark. Apply them in order: measure, remove the lock hold, claim rows without blocking, partition the ledgers, shrink the time index, and only then adjust autovacuum and memory. The database that survives a flash sale is not the one with the most aggressive settings, it is the one that never held a lock longer than it had to.
