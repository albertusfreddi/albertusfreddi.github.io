Designing Sub-50ms Payment Fraud Detection for Indonesian Fintech

16 min read • 2026-10-22

Production context: This is the fraud stack we run for an Indonesian e-wallet and a P2P lending platform, together processing roughly 3.2 million payment events per day. It scores every event inline in under 50ms, blocks about 0.9% of flagged volume, and keeps the false-positive friction rate at 0.31%. No registrar can run a payment rail in Indonesia without BI (Bank Indonesia) and OJK alignment, so every decision here is auditable.

Why Indonesian Fraud Looks Different

Fraud models built for US card rails fail here for a concrete reason: Indonesia is a QRIS and virtual-account market, not a card-present market. The dominant instruments are QRIS (the national QR standard), bank and e-wallet virtual accounts (VA), and wallet-to-wallet transfers. Card fraud rules built around CVV, BIN, and 3-D Secure simply have no matching signal.

The actual threat classes we defend against, in order of observed volume:

  • QRIS dynamic-QR tampering: an attacker takes a merchant's static QR, replaces the beneficiary, and re-presents it to buyers. The buyer scans a valid-looking QRIS that settles into the attacker's wallet.
  • Account takeover (ATO): credential stuffing and SIM-swap attacks then funnel money out through instant wallet transfers before the victim notices.
  • Mule-account networks: hundreds of KYC-passed accounts opened with stolen or rented identities, used only to receive and immediately drain fraudulent transfers.
  • High-velocity card testing and micro-transaction probing: attackers probe merchant checkouts with tiny amounts to map which wallets and VAs accept which rails.

The unifying property of all four is velocity. A single event looks innocent. The pattern of many events across a short window, a device, or an IP is what exposes the fraud. That single observation drives the entire architecture below.

The Latency Budget Is the Real Architecture

Every payment event must return an allow, block, or step-up decision inline. BI's QRIS settlement rules and the checkout experience both push toward a hard target: 50ms end to end for the inline decision, and 200ms for the richer post-hoc path. A deep neural model scoring hundreds of features will not fit that window, so the stack is layered by cost and latency.

LayerLatencyWhat it doesWhere it runs
Deterministic rules1-3msHard blocks: blacklist, velocity ceilings, amount anomaliesIn-process, memory
Feature lookup + gradient model6-15msRisk score from precomputed featuresRedis + in-memory model
Graph / link analysis20-45msMule detection, shared-device clustersRedisGraph or precomputed edges
Post-hoc enrichment200ms+Full device fingerprint, watchlist, sanction screeningAsync queue

The trick that keeps the inline path fast is feature precomputation. A background stream job recomputes every account, device, and IP feature every few seconds. The inline scorer never computes features from raw logs. It does a handful of HGETALL and ZRANGE calls on Redis, feeds the vector to a small gradient-boosted model, and thresholds the score. That is the entire 50ms path.

Redis Velocity Engines

Velocity signals are the workhorse of the system. Three counters matter most, and all of them are sliding windows implemented as Redis sorted sets scored by event timestamp. A sorted set gives you range queries by time for free, which is exactly what a sliding window needs.

Sliding-Window Velocity Counter (Redis Sorted Sets)
import redis
import time

r = redis.Redis(host="127.0.0.1", port=6379, decode_responses=True)

WINDOWS = {
    "1m": 60,
    "10m": 600,
    "1h": 3600,
}

def record_event(key: str, now: float | None = None) -> None:
    now = now or time.time()
    member = f"{now:.6f}:{r.incr(f'{key}:seq')}"
    pipe = r.pipeline()
    for label, secs in WINDOWS.items():
        zset = f"velocity:{key}:{label}"
        pipe.zadd(zset, {member: now})
        # trim everything older than the window
        pipe.zremrangebyscore(zset, 0, now - secs)
    pipe.execute()

def velocity(key: str, seconds: int) -> int:
    now = time.time()
    return r.zcount(f"velocity:{key}:latest", now - seconds, now)

The three counters that carry the most signal:

  • Account velocity: number of transfer attempts by a single account in 10 minutes. Legit users rarely exceed single digits. ATO attacks routinely hit 30 plus.
  • Device velocity: number of distinct accounts touched by one device fingerprint in an hour. Legitimate shared devices (households, warungs) touch 2 to 3 accounts. Mule rings push 40 to 100.
  • IP velocity: distinct accounts and merchants hit from one IP across 10 minutes. This catches credential-stuffing waves against a single rail.

Each counter is cheap, but combining them with a rule like device touches 10+ accounts while IP spans 4+ provinces is what turns raw counts into near-certain fraud. The rule catalog is deliberately small, around 70 hand-tuned rules, because every rule must be explainable in an audit.

Feature Store Before Model

An inline model is only as good as the features cached in front of it. We use an offline feature store (a Postgres table with a scheduled Spark job) that emits compact feature records to Redis as hashes. One hash per account, one per device, one per IP.

Feature Hash Layout (what the inline scorer reads)
# Redis hash: features:acct:{account_id}
# Redis hash: features:dev:{fingerprint}
# Redis hash: features:ip:{ip}

ACCT_FEATURES = [
    "acct_age_seconds",       # KYC-to-now age
    "txn_count_7d",
    "txn_amount_max_7d",
    "device_count_7d",        # distinct devices
    "province_count_7d",      # distinct provinces
    "avg_balance_floor",      # rolling min of balance
    "beneficiary_distinct_7d",
    "failed_auth_1h",
    "sim_changed_7d",         # from telco MSISDN feed
]

Two of these features deserve emphasis because they are Indonesia-specific:

  • sim_changed_7d comes from a telco MSISDN-churn feed. SIM swap is the leading indicator of a pending ATO, and it is a signal most Western fraud stacks never see.
  • beneficiary_distinct_7d is the counter of how many different accounts a user has paid in a week. A KYC-passed account that suddenly pays 60 distinct strangers is a mule, not a consumer.

The model itself is a small LightGBM ensemble (about 40 trees, max depth 5) trained on 18 months of labeled events. Small on purpose: it must load from memory in microseconds and its decisions must be reconstructible for the regulator. A 1,000-feature neural net would eke out fractions of a point of recall and cost you the ability to explain any single decision.

QRIS-Specific Defenses

Dynamic-QR tampering is the fraud type most specific to this market. The defense has three parts, and only one of them is a model:

  1. Merchant QR fingerprinting: every presented QRIS payload is hashed against the merchant's registered payment profile. A mismatch between the QR's embedded beneficiary and the merchant's KYC record fails instantly, before any model runs.
  2. Beneficiary graph consistency: a QR that routes to a wallet with a 2-week account age, an empty merchant profile, and no registered outlet is blocked outright. Most tampered QRs route to exactly that kind of account.
  3. Scan-settle time delta: legitimate QRIS payments settle within a few seconds of the scan. A QR presented, then settled 40 minutes later from a different device, is a strong signal of a re-presented code.

What makes this work is that the checks are deterministic and cheap. They do not need a score. They run as rules in the first 3ms layer, so a tampered QR is dead before the model even wakes up.

Mule Networks as a Graph Problem

Mule accounts are the hardest class because each account individually passes KYC and shows normal-looking volume. The fraud only appears when you look at the links between accounts: shared devices, shared IPs, shared beneficiary chains, and funds that move account to account with no commercial purpose.

We model this as a graph and precompute two labels per account:

  • Community membership: accounts are clustered by shared device and IP into connected components. A component of 80 accounts feeding a single sink is a mule ring regardless of what any one account looks like.
  • Layered-hop distance: an account within 1 or 2 hops of a known fraud sink gets a risk boost. When a fraud sink is confirmed, we fan the label out to its neighbors in the graph.
Graph Label Propagation to Neighbors
def propagate_risk(seed_accounts, hops=2, risk_delta=0.4):
    """Fan out risk from confirmed fraud sinks to their graph neighbors."""
    frontier = list(seed_accounts)
    seen = set(seed_accounts)
    for hop in range(1, hops + 1):
        next_frontier = []
        for acct in frontier:
            neighbors = graph_neighbors(acct, edge_types=["device", "ip", "transfer"])
            for nb in neighbors:
                if nb in seen:
                    continue
                seen.add(nb)
                # decay the risk with each hop
                add_risk(nb, risk_delta / (hop ** 2))
                next_frontier.append(nb)
        frontier = next_frontier

The graph does not run inline for every event. It runs as a daily batch plus a streaming delta on a RedisGraph instance. The inline path just reads each account's precomputed community_risk feature alongside the others.

Step-Up Beats Hard Reject

Hard-rejecting an ambiguous event adds friction to good users and teaches fraudsters where the tripwires are. The system returns one of three verdicts, and the middle one does the real work:

  • ALLOW: score below threshold, no action.
  • STEP_UP: score in the uncertain band. The user is pushed to OTP, biometric, or a WhatsApp confirmation. If they pass, the transaction proceeds and their account trust is nudged up.
  • BLOCK: score above the hard block threshold, or a deterministic rule fired.

The uncertain band is tuned so that about 1.2% of events land in STEP_UP, and roughly 72% of those clear the challenge. That keeps the genuine-friction rate at the 0.31% cited up top, which is the number that actually matters for retention. Fraud teams that over-index on recall and block aggressively churn their own good users off the platform.

Compliance and the Audit Trail

In Indonesia this is not optional polish. BI requires PSPs to hold fraud-management controls, and OJK's anti-money-laundering rules require that every suspicious-transaction report be backed by a reconstructible decision. The system writes a decision record for every event:

  • The feature vector that was scored, with timestamps of when each feature was computed
  • The exact rules that fired, with their thresholds and values
  • The model version, seed value, and the raw score before thresholding
  • The final verdict and the step-up challenge, if any

This record is written to an append-only store and retained for five years. When BI asks why a particular transfer was blocked, the answer is a single row, not a conversation. The model versioning discipline is the part most teams skip and the part regulators actually check.

What We Got Wrong First

Two honest failures from the first version, because they are the mistakes you will make too:

  1. We scored on stale features. The first build read raw event logs inline, which added 400ms and spilled the 50ms budget on peak days. The fix, feature precomputation, is now the system's backbone.
  2. We tuned the model on fraud latency, not friction. Early blocks hit a 4% false-positive rate mainly because recall was the hero metric. Customer support tickets told the real story. We re-tuned on genuine-user friction and fraud losses recovered within a quarter.

The pattern worth internalizing: the hard part of payment fraud is not the model. It is the latency budget, the velocity features, and the discipline to run the whole thing as explainable, auditable rules plus one small model.

Key Takeaways

  1. Indonesian fraud is velocity fraud, not card fraud. QRIS, VA, and wallet transfers mean your signals are account, device, and IP velocity, plus SIM-swap churn.
  2. Feature precomputation is the architecture. The 50ms inline path only works when features are cached, never computed on demand.
  3. Deterministic checks kill QRIS tampering. Fingerprint the merchant QR and validate the beneficiary graph before any model runs.
  4. Mules are a graph problem. Model account communities and hop distance to known sinks; they hide in the links, not the rows.
  5. Step-up beats hard reject. A 0.31% friction rate beats a 4% one for retention, and the regulator still gets its audit trail.
