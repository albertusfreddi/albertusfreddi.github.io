Why We Chose Supabase Edge Functions Over AWS Lambda for Real-Time Dashboards

16 min read • 2026-09-26

Production context: This is the read path behind an executive dashboard for an Indonesian distribution firm. Fifteen screens poll a single API for last-mile shipment status, warehouse throughput, and open invoice totals, refreshed several times an hour by a sales operations team. The old stack was Node.js on AWS Lambda behind API Gateway, with the database in a VPC. It averaged 450ms per request from Jakarta, sometimes more than a second when a cold start stacked on top of a database reconnect. We moved the read path to Supabase Edge Functions, and the same screens now return in 42ms at p95. This is the honest engineering comparison of the two, the parts that actually decide the latency, and the one thing on each side that would make us switch back.

The Cold Start Difference Is Real, but It Is Only Half the Story

The number everyone quotes about serverless is cold-start time. The claim worth unpacking is not "Lambda is slow" but "where does the latency actually come from, and which of those causes does an edge function remove". A Node.js Lambda request that touches a VPC database spends its time on several distinct things: the container or microVM starting, the runtime initialising, then the code establishing a fresh database connection, then the query, then the response. The cold start is only the first two.

An edge function removes most of the container start because it does not run in a container at all. It runs in an isolate inside a long-lived process, which is the same reason a browser tab can open a web worker in milliseconds. The V8 isolate is initialised from a pre-warmed snapshot, and on our load it added effectively nothing measurable to the request. The database reconnect, which was quietly half of our old latency, is a separate problem with its own fix, and I address it below, because moving runtimes does not fix it by itself.

The honest framing is not "isolates beat containers". It is that our old stack paid three taxes, and the migration removed two of them directly and let us remove the third with a pooler. The latency number in the title did not change by magic; it changed because we stopped paying a tax we had been paying without knowing which coin it was.

V8 Isolates vs Containerised MicroVMs, in Timing Terms

When a request arrives at a Lambda, the platform can keep a warm instance ready, or it has to place the request on a new one. A new instance means a microVM that boots a kernel, starts the runtime, reads your handler, and only then runs it. The typical number for a Node.js Lambda outside a VPC is hundreds of milliseconds; inside a VPC it is often over a second because the elastic network interface has to attach before anything else.

An edge function isolates do not boot a kernel and do not attach a network interface at request time. They are slices of a running process. The measurable effect we saw was that the request-to-request variability collapsed. Where the old stack had a pleasant 120ms floor and an occasional 1.4s spike, the edge function sits in a narrow band between 30ms and 60ms. For a dashboard that people glance at a dozen times a day, the spike is what erodes trust far more than the average, because the average hides the exact moment a user is waiting.

For a read-heavy dashboard that only talks to Postgres, none of the Lambda strengths matter and all of its taxes do.

The Query Path We Actually Deployed

The function is thin on purpose. It receives a JSON Web Token from the client, validates it, uses it to talk to Postgres with row-level security so the customer's own data is enforced by the database rather than by our code, and returns the KPI rows. The entire handler is under forty lines because the platform is doing the security-critical work.

The dashboard read endpoint
Deno.serve(async (req) => {
  const authHeader = req.headers.get("Authorization");
  if (!authHeader) {
    return new Response(JSON.stringify({ error: "missing token" }),
      { status: 401,
        headers: { "Content-Type": "application/json" } });
  }

  const supabase = createClient(
    Deno.env.get("SUPABASE_URL"),
    Deno.env.get("SUPABASE_ANON_KEY"),
    { global: { headers: { Authorization: authHeader } } }
  );

  const { data, error } = await supabase
    .from("executive_kpis")
    .select("metric_key, metric_value, updated_at")
    .order("updated_at", { ascending: false })
    .limit(20);

  if (error) {
    return new Response(JSON.stringify({ error: error.message }),
      { status: 500,
        headers: { "Content-Type": "application/json" } });
  }

  return new Response(JSON.stringify(data), {
    headers: {
      "Content-Type": "application/json",
      "Cache-Control": "s-maxage=30",
    },
  });
});

Three lines are doing more work than they look like. The global.headers option forwards the caller's token into the Postgres connection as the request context, which is what makes row-level security work. The s-maxage=30 header off-loads repeat reads to the edge cache, so a fifteen-screen dashboard refreshing in the same minute does not re-run the same query fifteen times. And the Deno.env.get calls read secrets that are stored in the project, never in the source, so the deploy package contains no credential.

Row-Level Security Moves the Access Boundary into the Database

The old Lambda had a long, hand-written authorisation layer that checked, per query, whether the caller belonged to the right distributor org. It was a source of bugs precisely because it had to be remembered in every handler. The edge function removes that entire layer by letting Postgres enforce it.

RLS binds each row to the caller's org automatically
ALTER TABLE executive_kpis ENABLE ROW LEVEL SECURITY;

CREATE POLICY org_read
  ON executive_kpis
  FOR SELECT
  TO authenticated
  USING (org_id = (auth.jwt() ->> 'org_id')::uuid);

What this buys is not just shorter code; it is a boundary that cannot be forgotten. The auth.jwt() call reads the caller's identity out of the same token the function forwarded. If a future engineer adds a new query and forgets a manual check, the database still returns only the caller's own rows, because the policy is on the table, not on the handler. In the old stack a forgotten check was a data leak; in this one it is a non-event. That is the kind of change that shows up in a security review as an entire class of finding disappearing.

The Connection Pooler Is the Real Latency Fix

Here is the part most migration write-ups skip. A serverless function by itself does not fix the database connection problem; it can even make it worse, because every concurrent isolate that opens its own Postgres session burns a connection and adds a full handshake to that request's tail. Our old VPC Lambda paid roughly 150ms of database connect time on top of every cold start because each instance maintained its own connections.

Supabase's answer is a transaction-mode pooler in front of Postgres. The function opens a lightweight pooler connection, not a session to the database itself, and the pooler multiplexes many isolates onto a small number of real database sessions. The handshake cost drops from per-request to per-session, and the risk of exhausting Postgres's finite connection limit drops to near zero at dashboard traffic volumes.

ModelConnection per isolateExhaustion riskBest for
Session poolingone real session eachhigh at scalestateful, long transactions
Transaction poolingshared, multiplexedlowstateless HTTP reads

The catch is that transaction pooling forbids things that assume a durable session, notably SET state and advisory locks that live beyond a single transaction. Our read path does neither, so transaction mode is correct. A dashboard endpoint that only selects rows is exactly the workload transaction pooling was built for, which is why the fit was clean instead of forced.

Cost Is Not the Main Reason, but It Drops Anyway

We did not run this migration to save money, and I want to be clear about that, because cost is usually quoted as the headline and it is the least interesting part. The old bill was a stack of small line items: API Gateway requests, Lambda invocations and duration, VPC endpoints, NAT gateway hours, and the CloudWatch logs that grew every month whether we read them or not. The new bill is one flat project fee with the functions, database, and pooler in it, and it is a fraction of the old total.

The more durable saving is operational, not financial. The old stack had six distinct resources that had to stay in agreement: the function, its IAM role, the layer with the Postgres client, the VPC configuration, the API Gateway route, and the log group. A deploy touched most of them and failed occasionally on one. The edge function is one file pushed by one command, and its secrets and pooler are configured once in the project. Fewer moving parts is the real saving, and it is the one that compounds monthly.

What Would Make Us Switch Back to Lambda

The decision is honest only if we state the reverse conditions, so here they are. We would move a workload back to Lambda when any of three things is true. First, the workload needs a native binary or a very long, memory-heavy computation that does not fit an isolate's modest limits; a data-processing step that spins for minutes belongs on a container or a queue runner, not an edge function. Second, the workload requires durable per-instance session state, which an edge function and transaction pooling both forbid. Third, the organisation already runs its entire security posture inside AWS and needs everything under one audit boundary; then the marginal latency is a smaller cost than the compliance story.

None of those are true for a dashboard read path. That is the actual lesson: the right answer is not "edge functions are better". The right answer is "match the runtime tax to the workload, then fix the database connection tax separately, because no runtime choice removes it by itself". Most teams that are unhappy with serverless latency are not unhappy with their runtime; they are unhappy with a database reconnect they never measured, and they are one pooler away from a much better number.

Measuring the Migration So the Number Means Something

We did not trust the title claims either. Before cutting over, we recorded the old endpoint's latency distribution for a week, and after cutover we recorded the new one for a week, and the comparison is what it is rather than what a vendor benchmark promised.

The measurement discipline matters more than the specific numbers. We sampled not just the mean but the full tail, because a dashboard's perceived slowness lives in the tail, and we measured from a probe in Jakarta against the production URL rather than from a shell in the same region. If you are going to claim a latency improvement, measure end to end, from the same place your users actually sit, and record the distribution, not a single lucky pull.

A tail-aware probe of the live endpoint
import asyncio
import httpx
import statistics

async def sample(url, n=200, token=None):
    headers = {"Authorization": "Bearer " + token} if token else {}
    async with httpx.AsyncClient() as client:
        times = []
        for _ in range(n):
            start = asyncio.get_event_loop().time()
            await client.get(url, headers=headers)
            times.append(asyncio.get_event_loop().time() - start)
    times.sort()
    return {
        "p50_ms": round(times[len(times)//2] * 1000, 1),
        "p95_ms": round(times[int(len(times)*0.95)] * 1000, 1),
        "max_ms": round(max(times) * 1000, 1),
    }

The probe is deliberately blunt: real HTTP requests with the real auth header, no warm-up that fakes a best case. The p95 it prints is the number we quote, because p95 is the highest latency a user experiences before they hit the unlucky tail, and it is far more meaningful to a product owner than an average nobody feels.

What We Would Reuse and What We Would Not

We would reuse three decisions without changing them: the thin-handler pattern that pushes access policy into the database via row-level security, the transaction-mode pooler, and the s-maxage edge cache that collapses repeat reads. Those three are what actually carry the latency number. We would not have re-created the dashboard's write path on edge functions, because writes need idempotency logic and occasionally longer transactions that the model was not optimised for, and we would not have migrated all at once; keeping one read screen cut over at a time gave us a small blast radius and an hour-by-hour comparison instead of a big-bang swap. The durable lesson is short: serverless latency is usually two taxes in a trench coat, and you only get to remove the runtime tax once you have measured the database one.
