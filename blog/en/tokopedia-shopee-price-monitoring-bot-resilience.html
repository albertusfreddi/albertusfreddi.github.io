Building Resilient Price Trackers for Indonesian Marketplaces in 2026

16 min read • 2026-10-22

Production context: This is the price-monitoring service we operate for around sixty Indonesian consumer brands. On a normal day it tracks roughly forty thousand SKUs across Tokopedia, Shopee, Blibli, and Lazada, and it raises a MAP-violation alert when a reseller lists below the agreed floor price by more than five percent. The constraint that shapes every decision below is not "can you read the price." It is "can this still be running in eight months, unattended, without burning a single account."

Why Every Price Tracker Dies the Same Way

The first version of almost every tracker looks like this: a loop over SKUs, one HTTP client, one cookie jar, a short sleep between calls. It works for two days. Then one morning the cron job reports success, the database fills with new rows, and the dashboard goes flat. Nobody notices for a week because "the job ran."

What actually happened is that the platform's bot-detection layer classified the session and started returning a challenge page or a structurally valid but empty JSON payload. The scraper, written to check response.status_code == 200, wrote thousands of rows containing None for price. The job succeeded. The data was worthless.

The failure has three distinct layers, and each needs its own defense:

  • Transport: the request never reaches product data. TLS fingerprint mismatch, missing headers, a challenge page, or a hard 403.
  • Payload: HTTP 200, but the JSON schema changed, the item was delisted, or the session returned a degraded response with an empty data array.
  • Semantics: the price came back, but it is the wrong price: a flash-sale price, a voucher-adjusted price, or a price for the wrong variant because the SKU mapping drifted.

Most trackers only defend the first layer. That is why they look healthy while they are wrong.

Model the Crawler as Three Budgets, Not a Loop

The mental model that fixed our reliability was to stop thinking of the crawler as a list of URLs and start thinking of it as a system that spends three separate budgets on every request:

BudgetWhat it limitsWhat happens when it runs dry
Request budgetTotal requests per minute across the whole fleetRequests queue instead of firing; no burst ever reaches the platform
Retry budgetAttempts allowed per SKU per cycleThe SKU is marked stale rather than hammered; it retries next cycle
Session budgetRequests a single session may make before retirementThe session is drained and rotated out before the platform flags it

The key property is that all three are enforced in one place, ahead of the network call. If you enforce rate limits by sleeping inside the scrape function, you cannot reason about total load, and a retry storm silently multiplies your traffic.

Token bucket with a shared Redis counter
import time
import redis

class FleetBudget:
    """A shared token bucket so every worker spends from one quota."""

    def __init__(self, r: redis.Redis, key: str, rate_per_min: int):
        self.r = r
        self.key = key
        self.rate = rate_per_min
        self.capacity = rate_per_min  # one minute of tokens

    def acquire(self, tokens: int = 1) -> float:
        """Block until tokens are available. Returns seconds waited."""
        start = time.monotonic()
        while True:
            now = time.time()
            # Lua keeps refill + spend atomic across all workers.
            script = """
            local key = KEYS[1]
            local rate = tonumber(ARGV[1])
            local cap = tonumber(ARGV[2])
            local want = tonumber(ARGV[3])
            local now = tonumber(ARGV[4])
            local state = redis.call('HMGET', key, 'tokens', 'ts')
            local tokens = tonumber(state[1]) or cap
            local ts = tonumber(state[2]) or now
            local elapsed = math.max(0, now - ts)
            tokens = math.min(cap, tokens + elapsed * (rate / 60.0))
            if tokens >= want then
                tokens = tokens - want
                redis.call('HMSET', key, 'tokens', tokens, 'ts', now)
                redis.call('EXPIRE', key, 120)
                return 1
            end
            redis.call('HMSET', key, 'tokens', tokens, 'ts', now)
            return 0
            """
            if self.r.eval(script, 1, self.key, self.rate, self.capacity, tokens, now):
                return time.monotonic() - start
            time.sleep(0.05)

Two details matter here. First, the refill and the spend happen inside one Lua script, so two workers can never read the same token balance and both spend it. Second, the bucket drains at the fleet rate, not the per-worker rate, which means adding workers does not increase the load you send to the marketplace. That is the whole point: scaling out your crawler should add throughput on your side, not traffic on theirs.

What Actually Blocks You, Layer by Layer

In our logs, blocks cluster into four causes. Knowing which one you hit determines the fix, and guessing wrong costs days.

1. TLS and HTTP/2 Fingerprinting

Before the platform reads a single header, it can inspect the shape of your TLS handshake: cipher suite order, supported groups, ALPN list, HTTP/2 settings, header ordering. A request from python-requests with default OpenSSL settings has a fingerprint that matches no real browser, and a serious anti-bot layer scores it before your User-Agent string is even parsed.

Changing the User-Agent does nothing. You need a client whose handshake matches a browser. In Python that means a client offering browser-grade TLS impersonation, or driving a real browser. We use the former for about 90 percent of traffic because it is roughly an order of magnitude cheaper per request than a headless browser.

Session factory with a browser-shaped fingerprint
from curl_cffi import requests as cffi_requests

BROWSER_PROFILES = ["chrome124", "chrome120", "safari17_0"]

def new_session(profile: str):
    # impersonate ties TLS cipher order, ALPN, and header order together.
    s = cffi_requests.Session(impersonate=profile)
    s.headers.update({
        "Accept-Language": "id-ID,id;q=0.9,en-US;q=0.8,en;q=0.7",
        "Accept": "application/json, text/plain, */*",
        "Origin": "https://www.tokopedia.com",
        "Referer": "https://www.tokopedia.com/",
    })
    return s

Note the locale header. A browser in Jakarta sends id-ID first. A crawler sending en-US from an Indonesian IP is a small inconsistency, and small inconsistencies are exactly what scoring models aggregate.

2. Challenge Interstitials

Turnstile and its equivalents do not always return HTTP 403. Often they return 200 with an HTML document containing a challenge script and no product data. Your parser then throws a KeyError, or worse, writes nulls.

Detect the challenge as a first-class state, before parsing:

Classify the response before you trust it
import re

CHALLENGE_MARKERS = (
    "cf-chl", "challenges.cloudflare.com", "turnstile",
    "captcha-delivery", "px-captcha", "are you a robot",
)

def classify(resp) -> str:
    """Returns: ok | challenge | blocked | empty | error"""
    body = resp.text or ""
    ctype = resp.headers.get("content-type", "")
    if resp.status_code in (401, 403, 429):
        return "blocked"
    if any(m in body.lower() for m in CHALLENGE_MARKERS):
        return "challenge"
    if "application/json" not in ctype:
        return "challenge" if "html" in ctype else "empty"
    try:
        payload = resp.json()
    except ValueError:
        return "empty"
    if not payload.get("data"):
        return "empty"
    return "ok"

When classify returns challenge, the correct action is to retire that session immediately and take a fresh one from the pool. Retrying on the same session deepens the score against it. This single rule cut our challenge rate from a slow climb to a flat line.

3. The Dynamic Token Problem

Marketplace web clients do not call a clean REST endpoint. They call a GraphQL endpoint whose requests carry a token embedded in the page bundle and rotated on deploys. Copying the token from a blog post gets you a 400 within a week.

The stable approach is to derive the token from the page you are already loading, rather than hardcoding it:

Extract a rotating GraphQL token from the loaded document
import json
import re

TOKEN_PATTERNS = (
    r'"graphql_token"\s*:\s*"([^"]+)"',
    r'"token"\s*:\s*"([A-Za-z0-9_\-]{20,})"',
    r'name="csrf-token"\s+content="([^"]+)"',
)

def scrape_token(html: str) -> str | None:
    for pattern in TOKEN_PATTERNS:
        m = re.search(pattern, html)
        if m:
            return m.group(1)
    # Many bundles ship the token inside a JSON blob in a script tag.
    for blob in re.findall(r'<script[^>]*type="application/json"[^>]*>(.*?)</script>', html):
        try:
            data = json.loads(blob)
        except ValueError:
            continue
        token = data.get("props", {}).get("pageProps", {}).get("token")
        if token:
            return token
    return None

Two rules make this durable. Store the token with the session, not globally, because tokens are usually bound to a session cookie. And treat a 400 with a token-shaped error as "refresh token, retry once," not as a permanent failure. A retry that first refreshes the token succeeds; a blind retry does not.

4. Rate Limits That Do Not Announce Themselves

Marketplaces rarely return a clean 429 with a Retry-After header. More often they degrade: slower responses, then partial payloads with some fields null, then empty arrays, then a challenge. By the time you see 429, you have been flagged for minutes.

So monitor the degradation signal, not just the status code. Track, per session, a rolling success rate over the last twenty requests. When it drops below 85 percent, retire the session voluntarily, before it is banned. A session you retire is one you can reuse tomorrow. A banned session is gone and may take your IP reputation with it.

Session health scoring and voluntary retirement
from collections import deque

class SessionState:
    def __init__(self, session, profile: str):
        self.session = session
        self.profile = profile
        self.recent = deque(maxlen=20)   # True = ok, False = failed
        self.uses = 0
        self.retired = False

    def record(self, ok: bool):
        self.recent.append(ok)
        self.uses += 1

    @property
    def health(self) -> float:
        if not self.recent:
            return 1.0
        return sum(self.recent) / len(self.recent)

    def should_retire(self) -> bool:
        # Retire on sustained failure, or after a fixed number of uses,
        # whichever comes first. The cap prevents a slow-burn flag.
        return self.health < 0.85 or self.uses >= 900

The constant 900 is not magic. We tuned it by observing how many requests a healthy session could make before its success rate drifted, then set the retirement point comfortably below that. If you copy one idea from this article, copy this one: retire sessions on a schedule, not on failure.

Keeping the SKU Mapping Honest

Every marketplace gives you its own product identifier and its own variant tree. A brand's internal SKU "SHIRT-OLV-M" has to map to a Tokopedia product_id plus a variant combination, a Shopee item_id plus model_id, and so on. That mapping decays: sellers relist, variants get added, listings get merged.

We keep the mapping in Postgres with an explicit confidence column and a last-verified timestamp. A row that has not verified in seven days gets re-resolved by search before it is trusted again. The resolution step compares the listing title and image hash against the canonical product, not just the ID, because IDs get recycled by resellers.

Mapping table that admits it can be wrong
CREATE TABLE sku_listing_map (
    id             bigserial PRIMARY KEY,
    internal_sku   text NOT NULL,
    marketplace    text NOT NULL,
    listing_id     text NOT NULL,
    variant_key    text,
    confidence     numeric(3,2) NOT NULL DEFAULT 0.50,
    last_verified  timestamptz,
    is_active      boolean NOT NULL DEFAULT true,
    UNIQUE (marketplace, listing_id, variant_key)
);

CREATE INDEX ON sku_listing_map (internal_sku)
    WHERE is_active;

-- A scrape only alerts on prices from mappings we still trust.
SELECT m.internal_sku, p.price, p.captured_at
FROM sku_listing_map m
JOIN price_snapshot p ON p.mapping_id = m.id
WHERE m.is_active
  AND m.confidence >= 0.80
  AND m.last_verified > now() - interval '7 days'
  AND p.captured_at > now() - interval '15 minutes';

Pruning the Price You Recorded

This is the least glamorous part and the one that most often makes a tracker useless. The number on the page is not the price. It might be:

  • A strikethrough price next to a discounted one, and you parsed the wrong node.
  • A flash-sale price valid for two hours, real but not the list price your MAP policy cares about.
  • A price before voucher, while the checkout price is lower.
  • A price after a platform subsidy, which the brand does not control.

Record all of them as separate fields rather than collapsing to one number: list_price, sale_price, voucher_amount, flash_sale boolean, captured_at. Then the MAP rule becomes an explicit query instead of a heuristic buried in Python.

MAP violation as a query, not a judgment call
WITH latest AS (
    SELECT DISTINCT ON (internal_sku, marketplace)
           internal_sku, marketplace,
           COALESCE(sale_price, list_price) AS effective_price,
           flash_sale, captured_at
    FROM price_snapshot
    WHERE captured_at > now() - interval '6 hours'
    ORDER BY internal_sku, marketplace, captured_at DESC
)
SELECT l.internal_sku,
       l.marketplace,
       l.effective_price,
       f.floor_price,
       round((f.floor_price - l.effective_price) / f.floor_price * 100, 2) AS pct_below
FROM latest l
JOIN map_floor_price f USING (internal_sku)
WHERE l.effective_price < f.floor_price * 0.95
  AND NOT l.flash_sale          -- brand-approved promotions are excluded
ORDER BY pct_below DESC;

Excluding flash sales explicitly is what stops the alert channel from becoming noise. In our first month, 60 percent of "violations" were platform-run campaigns the brand had already approved. Nobody trusts an alert stream that cries wolf that often.

Proving the Data Is Alive

A tracker that silently returns nothing looks identical to a tracker that works, from the outside. The fix is a canary: a small set of SKUs you know exist, are in stock, and have a stable price. Scrape those first on every cycle. If a canary fails, the cycle is marked degraded and the alerting path fires immediately, before the main run wastes its budget.

Canary gate that runs before the main sweep
CANARY_SKUS = [
    ("tokopedia", "SHIRT-OLV-M"),
    ("shopee",    "SHIRT-OLV-M"),
    ("tokopedia", "MUG-CER-350"),
]

def cycle_is_healthy(scraper) -> bool:
    for marketplace, sku in CANARY_SKUS:
        result = scraper.fetch_price(marketplace, sku)
        if result.status != "ok" or result.price is None:
            alert("canary failed", marketplace=marketplace, sku=sku,
                  status=result.status)
            return False
    return True

We also assert on volume. If yesterday's run wrote 38,000 rows and today's wrote 4,000, that is a failure even though every individual request returned 200. A simple guard in the orchestrator catches it:

Volume regression guard
def assert_volume_ok(today_rows: int, median_7d: float) -> None:
    if median_7d == 0:
        return
    ratio = today_rows / median_7d
    if ratio < 0.80:
        raise RuntimeError(
            "row volume collapsed: %d today vs %.0f median (%.0f%%)"
            % (today_rows, median_7d, ratio * 100)
        )

The first version of this system, before the session budget and the canary gate, had a worst week of 41 percent incomplete cycles and two banned accounts. The rewrite did not make scraping faster. It made failure visible and cheap, which is the only thing that keeps an unattended crawler alive.

The Parts You Should Not Automate

Two boundaries are worth stating plainly, because a tracker that ignores them is a liability rather than an asset.

Respect the published rules. Check robots.txt and the marketplace's terms before you build. Where a platform offers an official API or an affiliate data feed, use it: it is more stable, it is contractually permitted, and the price is the same. Much of what people build scrapers for on Tokopedia and Shopee is available through official partner programs, and a brand with sixty SKUs usually qualifies.

Do not build around an explicit denial. If a platform deploys a challenge and you defeat it with a CAPTCHA-solving service, you have moved from "reading public data politely" to "circumventing an access control," and in Indonesia that changes the risk profile for the client, not just for you. Our rule is that a challenge means back off and reduce rate, not solve and continue. In practice, a properly budgeted crawler almost never triggers one.

The Order to Build This In

If you are starting from a loop that works for two days, do these in order and stop when your reliability is good enough:

  1. Add the three budgets, with the request budget shared in Redis across every worker.
  2. Add classify() so a challenge page is never parsed as data.
  3. Add per-session health scoring and voluntary retirement.
  4. Add the canary gate and the volume guard, so silence becomes an alert.
  5. Split price into its components and encode the MAP rule as SQL.
  6. Only then optimize throughput, by adding workers behind the same shared budget.

Steps one through four are what separate a demo from a service. They are also the steps nobody writes about, because they are not clever. They are just the difference between a cron job that runs and a system that tells you the truth.
