Building WhatsApp Chatbots for Indonesian Businesses

16 min read • 2026-10-07

Production context: A Jakarta coffee roastery runs three cafe outlets, an online store, and a wholesale arm. Customer service lived on three personal WhatsApp numbers staffed by rotating part-timers, so answers about stock, roast profiles, reseller pricing, and order status were inconsistent and stopped when the shift ended. We moved them to a single WhatsApp Business Cloud API number behind a webhook service: verified inbound messages, a conversation state machine for the high-volume flows, template-approved out-of-hours replies, and a clean handoff to a human with full context when the bot is out of its depth. The bot now resolves 73% of inquiries with no human, first response lands in under 30 seconds at any hour, and everything flows through Meta's official endpoint rather than an unofficial client that a policy change or a device ban could kill overnight.

Why the Cloud API Is the Only Foundation That Survives

There are two routes to WhatsApp messaging automation, and in Indonesia the cheaper-looking one is the more expensive in production. Unofficial libraries such as baileys or whatsapp-web.js drive a WhatsApp Web session in reverse-engineered fashion. They take minutes to demo and weeks to get you blocked: one number logged into two devices, or a burst of outbound messages, and Meta disables the number with no appeal. That is the wrong risk for a business whose customer relationship runs through the number.

The other route is the WhatsApp Business Cloud API, hosted by Meta and provisioned through Business Manager, or a Business Solution Provider who resells the same API with a friendlier dashboard. Both send through the same Graph API endpoints, the same message templates, and the same 24-hour customer service window. The engineering differences are only in who provisions the number and where the webhooks route. Everything below assumes the Cloud API path, because it is the only one that keeps the number alive.

Verify the Webhook Before You Believe It

Meta calls your webhook for two very different reasons. When you register the callback URL, it sends a verification handshake with hub.mode, hub.verify_token, and hub.challenge query parameters; you answer by echoing the challenge back, and only when the token matches the value you configured. After that, real events arrive as JSON with a signature header. A handler that does not branch on these two shapes will either fail verification forever or treat a spoofed request as a real customer message.

The signature check is the security boundary. Every event body is signed with your Meta app secret, delivered in the X-Hub-Signature-256 header as sha256=…. You recompute the HMAC over the raw bytes and compare in constant time. If you skip this, anyone who learns your webhook URL can send a forged message and your bot will answer as though a customer asked.

webhook.py : handshake plus HMAC signature verification
import hashlib, hmac, os, json

APP_SECRET = os.environ["WA_APP_SECRET"]
VERIFY_TOKEN = os.environ["WA_VERIFY_TOKEN"]

def verify_signature(raw_body, signature):
    # Header arrives as: sha256=
    if not signature.startswith("sha256="):
        return False
    expected = signature[len("sha256="):]
    computed = hmac.new(APP_SECRET.encode(), raw_body, hashlib.sha256).hexdigest()
    return hmac.compare_digest(computed, expected)

def webhook(request):
    # 1) Registration handshake: echo the challenge back.
    if request.query.get("hub.mode") == "subscribe":
        if request.query.get("hub.verify_token") == VERIFY_TOKEN:
            return request.query.get("hub.challenge")
        return "verification token mismatch", 403

    # 2) Real event: reject unsigned or badly-signed bodies first.
    signature = request.headers.get("X-Hub-Signature-256", "")
    if not verify_signature(request.body, signature):
        return "bad signature", 401

    payload = json.loads(request.body)
    dispatch(payload)
    return "ok", 200

Two details are easy to get wrong. The HMAC is computed over the raw, unmodified request bytes, not over the parsed JSON, so the framework must hand you the body before any middleware reformats it. And the comparison must be constant-time (hmac.compare_digest), not ==, so the timing of your answer does not leak how many bytes of the digest matched. Both are one line each and both are the difference between a bot that verifies and a bot that pretends to.

A State Machine, Not a Giant If/Else

The second classic failure is modeling a menu of topics as nested conditionals. The first version works: if the user says "price," call the price function; if "catalog," the catalog function. The third version does not: a user changes their mind mid-flow, asks a question that belongs to another topic, or responds with something the branch did not anticipate, and the bot either loops or throws them back to a dead start.

A conversation is a small state machine. Each state knows what it is waiting for and what the acceptable next states are, and the whole thing is keyed by the WhatsApp phone number in a session store. The transition table is data, so adding a flow becomes adding a row rather than a new nesting level.

state_machine.py : sessions and transitions as data
STATES = {
    "menu":    ["menu", "catalog", "price", "status", "agent"],
    "catalog": ["menu", "catalog", "price", "agent"],
    "price":   ["menu", "price", "agent"],
    "status":  ["menu", "status", "agent"],
    "agent":   [],
}

def advance(session, text):
    current = session["state"]
    intent = classify(text)  # small intent classifier, see below
    if intent not in STATES[current] and intent not in ("menu", "agent"):
        return reply("Saya kurang paham. Pilih: katalog, harga, cek status, atau bicara ke staf.")
    return route(intent, session)

def route(intent, session):
    if intent == "catalog":
        session["state"] = "catalog"
        return reply("Katalog minggu ini: Sumatra, Flores, Bali. Ketik nama untuk detail.")
    if intent == "price":
        session["state"] = "price"
        return reply("Harga retail atau reseller?")
    if intent == "status":
        session["state"] = "status"
        return reply("Kirim nomor pesanan Anda, contohnya KNR-1024.")
    if intent == "agent":
        return escalate(session)
    return reply_menu()

The state transitions live in STATES, the entry table, while route holds only the actions. That separation is what keeps the system readable at twelve flows instead of three. The session (session["state"] plus any collected fields such as the order number) persists in Redis with a 24-hour TTL per phone number, so a restart mid-conversation does not give the customer amnesia. When the number changes, the state changes; when the service restarts, it is restored.

For intent classification you do not need a model for two or three flows. A keyword matcher with light normalization is faster to build, cheaper to run, and far easier to debug in production. Reserve a small language model for open-ended questions you cannot enumerate, and route those to the agent channel rather than guessing.

Templates and the 24-Hour Customer Service Window

The single rule that surprises most builders: you cannot free-type any message at any time. After a customer messages you, the number may reply freely for 24 hours. Outside that window, only approved template messages are allowed, and Meta rejects a free-form send with a template-required error. This is not a quota or a pricing tier; it is the API contract, and it applies to the biggest accounts too.

Templates must be submitted and approved for the category, locale, and language, with placeholders written as {{1}}, {{2}}, and so on. In practice you pre-approve the handful the business actually uses: an order confirmation, an order-ready or status update, and an "our staff will reply shortly" fallback, each in Indonesian (id locale). The value you inject comes from your order system, not from customer text, so the templates stay generic enough to approve once and reuse thousands of times.

send.py : an approved template with parameters
import requests

def send_template(phone_number_id, access_token, recipient, template_name, lang, params):
    body = {
        "messaging_product": "whatsapp",
        "to": recipient,
        "type": "template",
        "template": {
            "name": template_name,
            "language": {"code": lang},
            "components": [{
                "type": "body",
                "parameters": [{"type": "text", "text": p} for p in params],
            }],
        },
    }
    r = requests.post(
        f"https://graph.facebook.com/v20.0/{phone_number_id}/messages",
        headers={"Authorization": f"Bearer {access_token}"},
        json=body,
    )
    r.raise_for_status()
    record_outbound(recipient, template_name, params)
    return r.json()

Notice the split between the fixed template and the injected parameters. The template body is the approved text; the parameters are the only thing that changes per order. If a parameter does not arrive from the order system, the code should not send the message at all rather than send a template with a blank slot to a real customer. Every outbound send is also recorded before it leaves, because the webhook will eventually call back with a delivery status and you need that outbound record to correlate against.

Queueing, Idempotency, and Backpressure

Graph API enforces a throughput limit per phone number, and it redelivers webhooks when your server does not acknowledge quickly. A bot that handles those two facts by praying is a bot that double-replies and drops messages during the lunch rush. The fix is two small, unglamorous pieces of infrastructure.

Idempotency: every inbound message event carries a unique message id. Store it in Redis with SET NX (only set if absent) before processing, and skip the event if the key already exists. A redelivered webhook then becomes a no-op instead of a duplicate reply.

dispatch.py : dedupe by message id before any side effect
def dispatch(payload, redis):
    value = payload["entry"][0]["changes"][0]["value"]
    messages = value.get("messages") or []
    if not messages:
        return  # a status update, not an inbound message

    msg_id = messages[0]["id"]
    # nx=True only claims the key if it was not there. A redelivery
    # finds the key present and returns without processing again.
    claimed = redis.set(f"seen:{msg_id}", "1", nx=True, ex=86400)
    if not claimed:
        return

    from_number = messages[0]["from"]
    text = messages[0]["text"]["body"]
    session = load_session(from_number)
    reply = advance(session, text)
    enqueue_outbound(from_number, reply)

Backpressure: outbound sends go through a queue keyed by the 24-hour window budget, not blasted straight at Graph API. A token bucket or a simple per-second pacing loop keeps the number under its throughput ceiling, so a burst of status updates to a thousand customers drains smoothly over minutes rather than tripping the limit and failing half of them. When a send fails with a retryable error, the job returns to the queue with exponential backoff and jitter instead of hammering the endpoint.

Human Handoff without Dropping Context

The honest way to use a bot is to give it an exit. When intent confidence is low, or the customer asks for a human, the system should escalate cleanly rather than stall in a loop. That handoff has three parts: freeze a summary of the conversation so far, park the session so a late customer message does not get answered by the bot a second time, and route to the first available human with the full thread attached.

Because the whole conversation ran through the same state machine and session store, the summary is already structured: state, collected fields, last three messages, and why it escalated. The human picks up inside the same WhatsApp thread, so the customer never repeats themselves. The metric to watch is not "conversations the bot handled" but "conversations the bot handled well"; an escalation that reaches a human with full context is a good outcome, not a failure.

The thread through all five rows is one discipline: a WhatsApp bot lives on the boundary of an external platform's rules, and it fails at that boundary far more often than it fails in the middle of its own logic. Verify what comes in, dedupe the things that arrive twice, stay inside the messaging window, and do not let your own throughput outrun the platform's. Those four habits remove most of the incidents that sink otherwise fine bots.

How to Start without Boiling the Ocean

Begin with one number and one flow. Pick the highest-volume inquiry, usually "where is my order" or "send me the catalog". Provision the Cloud API number through Business Manager or a local Business Solution Provider, wire the webhook with the handshake and signature check, and implement only that single flow with a human-exit escape. Pre-approve three templates. Run it for a week and measure two numbers: the share of that flow resolved without a human, and the number of escalations that reach a human with full context. When those two look healthy, add the next flow as a new row in STATES rather than a new branch, and keep templates pinned to what the business actually sends. The goal is not to replace every conversation; it is to make the repetitive ones instant and the complex ones land on a human who already knows the story.
