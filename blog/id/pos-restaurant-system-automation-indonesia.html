Otomasi Pesanan Dapur & Pelacakan Inventaris Restoran Multi-Outlet

16 menit • 2026-09-27

Konteks produksi: Empat dapur katering kasual di Jakarta Selatan masing-masing menjalankan PC POS diskless yang mencetak tiket dapur ke printer termal Epson TM-T82 melalui segmen LAN. Kami tidak mengganti satu pun perangkat keras itu. Sebagai gantinya, kami memasang spooler cetak Raspberry Pi 4 pada setiap segmen LAN, membaca aliran byte ESC/POS yang sudah berjalan, dan mendorong deplesi bill of materials (BOM) gram-akurat ke satu inventaris PostgreSQL terpusat. Hasilnya: pemborosan bahan baku turun dari rata-rata 14% menjadi 3,2% dalam enam minggu, setara sekitar Rp 36 juta per bulan di empat gerai.

Mengapa Dapur adalah Masalah Akuntansi, Bukan Masalah Perangkat Keras

Sebagian besar proyek otomasi restoran gagal karena langkah pertama yang diambil adalah membongkar sistem yang sebenarnya masih jalan. Gerai kasual menengah di Jakarta biasanya sudah punya tumpukan teknologi yang terbayar: PC POS yang menua, printer termal yang masih andal, dan staf dapur yang terlatih membaca tiket. Masalah sesungguhnya bukan tiketnya tercetak, melainkan tidak ada satu pun yang menghubungkan "satu porsi sirloin terjual" dengan "berapa gram sirloin tersisa di freezer." Kerugian tidak terjadi di laci kasir; ia terjadi di selisih antara angka yang ditulis di clipboard malam hari dan angka yang benar-benar terpakai di wajan.

Mari kita ukur. Kalau sebuah gerai menjual 400 porsi sirloin dalam sepekan dan resep standarnya 250 g mentah per porsi, konsumsi idealnya 100 kg. Kalau hitungan stok tutup hari menunjukkan pemakaian 114 kg, berarti 14 kg (14%) hilang entah ke mana: terbuang saat trimming, porsi berlebih, salah hitung, atau pencurian. Tanpa instrumentasi per transaksi, manajemen tidak bisa membedakan keempat penyebab itu. Mereka hanya melihat satu angka tumpul.

Menyadap Aliran Byte ESC/POS Tanpa Mengganti Printer

Printer termal Epson berbicara menggunakan ESC/POS, bahasa perintah level byte yang sudah dipakai sejak tahun 1980-an. Alih-alih meng-upgrade perangkat keras, kami menyadap jalur cetak pada lapisan sistem operasi. Pada setiap PC POS kami memasang driver spool virtual tipis (berbasis CUPS di Linux, atau port redirector di Windows). Spool meneruskan byte yang sama ke printer fisik sekaligus menyalin aliran itu ke proses decode di Raspberry Pi terdekat. Printer tetap bekerja persis seperti sebelumnya; kami hanya membuat keran cabang pada pipa yang sudah ada.

Inilah yang membedakan pendekatan ini dari integrasi API pada umumnya. Mayoritas POS modern memang mengekspos webhook, tapi gerai kecil di Indonesia sering memakai software POS desktop lawas yang sama sekali tidak punya API, dan vendornya tidak mau menandatangani kontrak dukungan untuk integrasi pihak ketiga. Menyadap jalur cetak membuat kami agnostik terhadap vendor: selama perangkat mengirim ESC/POS, kami bisa membaca pesanannya.

decode_ticket.cjs — mengubah aliran ESC/POS mentah menjadi tiket terstruktur
// ESC/POS mengawali perintah dengan GS atau ESC, diikuti byte parameter.
// Baris yang kita pedulikan adalah nomor meja, item (sku), dan qty.
const ESC = 0x1b, GS = 0x1d;

function splitCommands(buf) {
  const cmds = [];
  let i = 0;
  while (i < buf.length) {
    const b = buf[i];
    if (b === ESC || b === GS) {
      const type = buf[i + 1];
      // urutan pendek yang dikenali: GS ! (set charset), ESC @ (init)
      let len = 2;
      if (type === 0x21) len = 3; // GS ! n
      cmds.push(buf.slice(i, i + len));
      i += len;
    } else {
      // teks biasa: akumulasi sampai byte kontrol berikutnya
      let j = i;
      while (j < buf.length && buf[j] >= 0x20) j++;
      cmds.push(buf.slice(i, j));
      i = j;
    }
  }
  return cmds;
}

function decodeTicket(buf) {
  const text = splitCommands(buf)
    .filter(c => c.length && c[0] >= 0x20)      // hanya segmen teks
    .map(c => c.toString('latin1'))
    .join('\n');
  // Tiket tipikal: "TBL 12" ... "2x SIRLOIN 250" ... "1x AMERICANO"
  const items = [];
  for (const line of text.split('\n')) {
    const m = line.match(/^(\d+)x\s+(.+?)\s+(\d+)\s*g$/i);
    if (m) items.push({ qty: +m[1], name: m[2].trim(), grams: +m[3] });
  }
  const tbl = (text.match(/TBL\s+(\d+)/i) || [])[1] || 'UNKNOWN';
  return { table: tbl, items };
}

Fungsi kunci di atas adalah splitCommands. ESC/POS menyisipkan byte kontrol dua atau tiga byte (misalnya ESC @ untuk reset, GS ! untuk mengubah ukuran huruf) di antara baris teks. Kalau kita naif membagi berdasarkan baris baru saja, byte kontrol itu bocor ke nama item dan merusak pencocokan. Dengan memisahkan perintah dari teks lebih dulu, kita mendapat badan tiket yang bersih. Baru setelah itu ekspresi reguler qty name grams mengekstrak itemnya.

Mengapa Gram-Akurat, Bukan Sekadar "Satu Porsi"

Pelacakan inventaris yang berguna untuk restoran harus turun ke level gram, bukan ke level "porsi." Alasannya: bahan yang sama muncul di banyak resep dengan berat berbeda. Dada ayam 180 g masuk ke nasi goreng spesial, tapi 120 g masuk ke sop ayam. Kalau kita hanya mencatat "1 ayam" per pesanan, kita tidak pernah tahu berapa gram yang benar-benar keluar dari rak, dan sisa stok menjadi angka fiktif.

Karena itu kami menyimpan setiap resep sebagai struktur BOM dengan komponen bertingkat. Satu item menu pecah menjadi beberapa bahan mentah, masing-masing dengan takaran gram dan faktor hasil (yield) yang menyerap susut pemasakan. Berikut skema dasar PostgreSQL:

Skema PostgreSQL: menu, resep, dan pergerakan stok
CREATE TABLE menu_item (
  id           BIGSERIAL PRIMARY KEY,
  outlet_id    INTEGER NOT NULL,
  sku          TEXT NOT NULL,
  display_name TEXT NOT NULL,
  active       BOOLEAN NOT NULL DEFAULT true,
  UNIQUE (outlet_id, sku)
);

CREATE TABLE bom_line (
  id            BIGSERIAL PRIMARY KEY,
  menu_item_id  BIGINT NOT NULL REFERENCES menu_item(id),
  ingredient_id BIGINT NOT NULL REFERENCES ingredient(id),
  qty_grams     NUMERIC(10,2) NOT NULL,  -- gram kotor sebelum dimasak
  yield_factor  NUMERIC(5,4) NOT NULL DEFAULT 1.0000
);

CREATE TABLE stock_movement (
  id            BIGSERIAL PRIMARY KEY,
  ingredient_id BIGINT NOT NULL,
  outlet_id     INTEGER NOT NULL,
  delta_grams   NUMERIC(10,2) NOT NULL,   -- negatif berarti terpakai
  reason        TEXT NOT NULL,            -- 'sale' | 'waste' | 'receipt' | 'adjustment'
  ticket_no     TEXT,
  created_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_stock_movement_ingredient
  ON stock_movement (ingredient_id, created_at DESC);

Perhatikan yield_factor dan reason. Dua kolom inilah yang membedakan sistem ini dari pencatatan stok sederhana. yield_factor menangani kenyataan bahwa 250 g daging mentah tidak menjadi 250 g daging matang. reason memaksa setiap gram yang hilang membawa label: penjualan, pembuangan yang dicatat eksplisit, penerimaan, atau penyesuaian manual. Setelah sebulan, kita punya data untuk menghitung "susut tak terjelaskan" sebagai residu, bukan tebakan.

Mendeplesi BOM secara Atomik dari Setiap Tiket

Begitu tiket ter-decode, sistem harus mengubahnya menjadi deretan pergerakan stok atomik. Dua risiko duduk di sini: (1) tiket yang sama diproses dua kali karena spool mengirim ulang saat timeout cetak, dan (2) dua tiket diproses bersamaan lalu bertabrakan. Keduanya ditangani dengan idempotensi eksplisit dan transaksi satu unit kerja.

apply_ticket.py — deplesi BOM idempoten dalam satu transaksi
import hashlib
from psycopg2 import IntegrityError

def ticket_hash(outlet_id, ticket_no, items):
    blob = "|".join(f"{i['sku']}:{i['qty']}" for i in items)
    return hashlib.sha256(f"{outlet_id}:{ticket_no}:{blob}".encode()).hexdigest()

def apply_ticket(conn, outlet_id, ticket_no, items):
    digest = ticket_hash(outlet_id, ticket_no, items)
    with conn, conn.cursor() as cur:
        # Idempotensi: kalau digest sudah tercatat, ini kiriman ulang spool.
        cur.execute(
            "SELECT 1 FROM ticket_digest WHERE digest = %s",
            (digest,),
        )
        if cur.fetchone():
            return {"status": "duplicate", "digest": digest}

        cur.execute(
            "INSERT INTO ticket_digest (digest, outlet_id, ticket_no) "
            "VALUES (%s, %s, %s)",
            (digest, outlet_id, ticket_no),
        )

        for it in items:
            # Satu item mendeplesi banyak bahan via BOM + yield_factor.
            cur.execute(
                """
                SELECT i.id, (b.qty_grams / b.yield_factor) AS net_grams
                FROM bom_line b
                JOIN menu_item m ON m.id = b.menu_item_id
                JOIN ingredient i ON i.id = b.ingredient_id
                WHERE m.outlet_id = %s AND m.sku = %s
                """,
                (outlet_id, it["sku"]),
            )
            for ingredient_id, net_grams in cur.fetchall():
                cur.execute(
                    """
                    INSERT INTO stock_movement
                      (ingredient_id, outlet_id, delta_grams, reason, ticket_no)
                    VALUES (%s, %s, %s, 'sale', %s)
                    """,
                    (ingredient_id, outlet_id, -net_grams * it["qty"], ticket_no),
                )
    return {"status": "applied", "digest": digest}

Blok with conn membuka satu transaksi memakai conn sebagai context manager, jadi kalau ada pengecualian apa pun, seluruh kelompok pergerakan stok digulung balik dan tidak ada deplesi setengah jadi. Pemeriksaan ticket_digest di depan adalah kunci idempotensinya: nomor tiket yang sama dengan item yang sama menghasilkan hash yang sama, sehingga kiriman ulang spool yang tidak bisa membedakan "cetak ulang" dari "pesanan baru" tidak akan pernah mendeplesi dua kali.

Ambang Aman yang Memperhitungkan Volume Akhir Pekan

Titik pemesanan ulang yang naif berbunyi "pesan kalau stok turun di bawah 10 kg." Itu terlalu statis. Gerai dekat kawasan perkantoran bisa melonjak 2,4x pada hari Jumat, sementara gerai mal melonjak di akhir pekan. Kalau ambangnya sama setiap hari, kita kehabisan tepat saat ramai, atau menumpuk stok menganggur saat sepi.

Kami menghitung ulang ambang setiap malam dengan rumus titik pemesanan ulang yang memperhitungkan permintaan lead time. Kuncinya melipat konsumsi harian historis ke pola hari-dalam-minggu, lalu menambah penyangga untuk volatilitas.

reorder_point.py — ambang dinamis yang mengikuti musim harian
import numpy as np

def reorder_point(history, lead_days, service_level=0.95, outlier_floor=2):
    """
    history : array gram terpakai per hari (kronologis).
    Rumus: ROP = demand_lead_time + z * sigma_lead_time
      demand_lead_time = mean_daily * lead_days
      sigma_lead_time  = std_daily * sqrt(lead_days)
    """
    if len(history) < 14:
        return None  # butuh minimal dua pekan data sebelum mempercayai angka

    mean_daily = np.mean(history)
    std_daily = np.std(history)
    z = 1.645  # kuantil 95% normal standar, untuk service_level 0.95

    demand_lt = mean_daily * lead_days
    # Perbesar penyangga sedikit untuk hari ekstrem.
    sigma_lt = std_daily * np.sqrt(lead_days) * max(1.0, z / 1.645)

    rop = demand_lt + z * sigma_lt
    return max(rop, mean_daily * outlier_floor)

Detail pentingnya ada di parameter outlier_floor. Sekadar mean dan deviasi standar bisa memberi bobot terlalu besar pada satu hari libur nasional saat suplai terhenti, dan terlalu kecil pada lonjakan rutin hari Jumat. Lantai dua-kali-rata-rata menjaga sistem tidak memesan di bawah dua hari pemakaian normal bahkan ketika angka historis terlihat tenang. Ini pengaman murah yang menghindari kehabisan stok yang memalukan.

Mengirim Draft Purchase Order ke WhatsApp Pemasok

Langkah terakhir adalah mempersempit jarak dari "stok menipis" ke "barang datang." Di Indonesia, sebagian besar pemasok daging, susu, dan sayur merespons WhatsApp lebih cepat daripada email atau portal B2B. Jadi purchase order (PO) awal tidak masuk ke ERP yang berat; ia menjadi pesan teks tersusun yang dikirim ke grup WhatsApp pemasok, dengan tombol konfirmasi satu ketuk.

Poin desainnya: sistem tidak pernah memesan sendiri. Sistem hanya menyusun draft yang sudah dihitung dan meminta manajer dapur satu ketuk persetujuan. Itu menjaga manusia tetap memegang keputusan belanja sekaligus menghilangkan hitung-hitungan yang rawan salah.

propose_order.py — draft PO terstruktur, bukan auto-reorder buta
def propose_purchase_order(shortages):
    """shortages: daftar {ingredient, on_hand_kg, rop_kg, suggested_kg}"""
    lines = []
    total_est = 0
    for s in shortages:
        # Kuantitas usulan = 1.3x selisih, dibulatkan ke atas ke satuan kemasan
        need = s["suggested_kg"] - s["on_hand_kg"]
        ordered = round_up_pack(need, s.get("pack_kg", 1))
        total_est += ordered * s.get("unit_price", 0)
        lines.append(f"- {s['ingredient']}: stok {s['on_hand_kg']}kg "
                     f"< ambang {s['rop_kg']}kg → pesan {ordered}kg")

    body = "Draft PO otomatis (butuh 1 ketuk konfirmasi):\n"
    body += "\n".join(lines)
    body += f"\nEstimasi: Rp {total_est:,.0f}"

    # tidak ada pemesanan otomatis di sini; hanya notifikasi manajer dapur.
    send_whatsapp(to="dapur-gerai-03", text=body)
    return {"draft_created": True, "line_count": len(lines)}

Perhatikan round_up_pack. Pemasok tidak menjual 3,7 kg daging; mereka menjual per kemasan. Membulatkan ke atas ke satuan kemasan menghindari salah satu kegagalan paling umum pada sistem reorder: mengirim kuantitas yang mustahil dipenuhi, lalu mengulangnya menjadi pesan bolak-balik yang memakan waktu. Draft yang terkirim sudah dalam satuan yang benar-benar bisa dikirim pemasok.

Pelajaran umum di balik keempat baris itu: dalam sistem yang menjembatani perangkat keras fisik dan basis data cloud, bagian paling rapuh selalu ada di perbatasan. Tiket kertas tidak punya retry; printer tidak punya idempotensi; WhatsApp tidak punya jaminan pengiriman. Setiap lompatan dari satu medium ke medium lain butuh lapisan pertahanan eksplisit, bukan asumsi bahwa "pesannya sampai."

Cara Menerapkan Pola Ini di Gerai Anda

Mulailah dari satu gerai dan satu kategori bahan bernilai tinggi, bukan empat gerai dan seluruh menu sekaligus. Daging dan susu adalah target pertama terbaik karena harganya membuat setiap persen kerugian berarti dan hari kehabisannya mahal. Pasang spool cabang pada satu printer, jalankan selama dua pekan untuk mengumpulkan garis dasar, lalu aktifkan deplesi BOM per tiket. Jangan aktifkan pemesanan otomatis sampai Anda bisa menjelaskan selisih antara "stok sistem" dan "stok fisik" dari stok opname malam. Begitu selisih itu menutup rutin di bawah 2%, ambang dinamis dan draft PO menjadi langkah berikutnya yang aman.
