Membangun Agen AI RAG Produksi yang Menangani Bahasa Gaul Indonesia dalam Skala Besar

12 menit • 2026-10-22

Konteks Produksi: Sistem ini menangani 50.000+ query pelanggan per hari untuk platform e-commerce Jakarta dengan 2,3 juta pengguna aktif. Normalisasi bahasa gaul meningkatkan akurasi intent dari 67% menjadi 94,2%. Latensi end-to-end p95: 1,8 detik.

Mengapa Embedding Siap Pakai Gagal pada Bahasa Gaul Indonesia

Model embedding multilingual pre-trained (OpenAI ada-002, Cohere multilingual-v3, sentence-transformers) bekerja cukup baik pada teks formal Indonesia—artikel berita, Wikipedia, dokumen pemerintah. Tapi langsung ambruk pada query customer support percakapan.

Kasus kegagalan nyata: Pesan pelanggan "min paket sy blm smpe pdhl udh tf kmrn" menghasilkan vektor embedding dengan cosine similarity 0,31 terhadap artikel knowledge base "Tracking Paket Belum Sampai" (butuh 0,78+ untuk retrieval yang reliabel). Model tidak mengenali:

  • min → admin (customer service)
  • sy → saya
  • blm → belum
  • smpe → sampai
  • pdhl → padahal
  • udh → sudah
  • tf → transfer
  • kmrn → kemarin

Pipeline Normalisasi Bahasa Gaul Indonesia

Kami menyusun kamus 4.500 entri yang memetakan kontraksi kolokial, salah eja fonetik, dan imbuhan regional ke lemma bahasa Indonesia standar. Sumber:

  • Ekstraksi manual dari 50K log chat customer support (2024-2026)
  • Penambahan crowdsourcing dari tim CS (12 agen, Jakarta/Surabaya/Medan)
  • Korpus bahasa gaul Indonesia akademik (Universitas Indonesia, 2023)
  • Scraping media sosial (Twitter/X Indonesia trending, filter NSFW)

Implementasi menggunakan automaton Aho-Corasick untuk pattern matching O(n + m) (n = panjang input, m = jumlah match), dikompilasi sekali saat startup:

Normalizer Bahasa Gaul Produksi (Python)
import re
import ahocorasick
from functools import lru_cache

class IndonesianSlangNormalizer:
    def __init__(self, dictionary_path: str):
        self.automaton = ahocorasick.Automaton()
        with open(dictionary_path, 'r', encoding='utf-8') as f:
            for line in f:
                slang, formal = line.strip().split('\t')
                self.automaton.add_word(slang, (slang, formal))
        self.automaton.make_automaton()
    
    @lru_cache(maxsize=10000)
    def normalize(self, text: str) -> str:
        text = text.lower().strip()
        # Hapus karakter berulang (looool → lol, gaaakkkk → gak)
        text = re.sub(r'([a-z])\1{2,}', r'\1', text)
        
        # Replace slang via Aho-Corasick
        replacements = []
        for end_idx, (slang, formal) in self.automaton.iter(text):
            start_idx = end_idx - len(slang) + 1
            replacements.append((start_idx, end_idx + 1, formal))
        
        # Terapkan replacement dari belakang agar indeks tetap valid
        for start, end, formal in reversed(replacements):
            text = text[:start] + formal + text[end:]
        
        return text.strip()

# Penggunaan produksi
normalizer = IndonesianSlangNormalizer('/app/data/slang_dict.tsv')
raw_query = "min paket sy blm smpe pdhl udh tf kmrn"
normalized = normalizer.normalize(raw_query)
# Output: "admin paket saya belum sampai padahal sudah transfer kemarin"

Cache hit rate: 78% (pelanggan mengulang frasa serupa). LRU cache mengurangi latensi normalisasi dari 12ms → 0,8ms untuk query yang di-cache.

Edge case yang ditangani:

  • Word boundary: "minimum" tidak boleh match "min" → gunakan boundary \b di dictionary
  • Ambiguitas: "ya" bisa berarti "yes" atau "which" → disambiguasi via POS tagging (model spaCy Indonesia) hanya saat diperlukan (0,3% query)
  • Varian regional: "kok" Jawa (kenapa) vs "kok" Jakarta (terkejut) → konteks dari pesan sebelumnya di sesi

Arsitektur Retrieval Hybrid Dense-Sparse

Vector search murni gagal pada exact match: nomor order ("INV-2024-08-12345"), kode transfer bank ("BCA-771234567890"), SKU produk ("ASUS-ROG-STRIX-RTX4090"). Cosine similarity tidak menjaga ketepatan alfanumerik.

Solusi: Retrieval hybrid menggabungkan embedding dense (semantik) + keyword search BM25 (leksikal). Database vektor Qdrant mendukung keduanya secara native.

Qdrant Hybrid Search (Python SDK)
from qdrant_client import QdrantClient
from qdrant_client.models import (
    Distance, VectorParams, PointStruct,
    Query, QueryRequest, SearchRequest
)
import openai

client = QdrantClient(url="https://qdrant.internal.example.com")

# Indexing: simpan vector + full-text
def index_kb_article(article_id: str, text: str):
    vector = openai.Embedding.create(
        input=text, model="text-embedding-ada-002"
    )["data"][0]["embedding"]
    
    client.upsert(
        collection_name="support_kb",
        points=[PointStruct(
            id=article_id,
            vector=vector,
            payload={"text": text}  # Full-text di-index otomatis
        )]
    )

# Hybrid retrieval: gabung skor dense + sparse
def hybrid_search(query: str, top_k: int = 5) -> list:
    normalized_query = normalizer.normalize(query)
    query_vector = openai.Embedding.create(
        input=normalized_query, model="text-embedding-ada-002"
    )["data"][0]["embedding"]
    
    # Dense vector search (bobot: 0.7)
    vector_results = client.search(
        collection_name="support_kb",
        query_vector=query_vector,
        limit=top_k * 2
    )
    
    # Sparse BM25 search (bobot: 0.3)
    # ponytail: Qdrant 1.7+ BM25 native; versi lama pakai Elasticsearch eksternal
    bm25_results = client.query(
        collection_name="support_kb",
        query=normalized_query,
        limit=top_k * 2
    )
    
    # Reciprocal Rank Fusion (RRF) untuk kombinasi skor
    combined_scores = {}
    for rank, hit in enumerate(vector_results, 1):
        combined_scores[hit.id] = combined_scores.get(hit.id, 0) + 0.7 / (60 + rank)
    for rank, hit in enumerate(bm25_results, 1):
        combined_scores[hit.id] = combined_scores.get(hit.id, 0) + 0.3 / (60 + rank)
    
    # Sort by combined score, return top_k
    ranked = sorted(combined_scores.items(), key=lambda x: x[1], reverse=True)
    return [id for id, score in ranked[:top_k]]

Metrik produksi (50K query/hari):

  • Hybrid retrieval recall@5: 94,2% (vs 87% dense-only, 71% BM25-only)
  • Exact match retrieval (nomor order): 99,8% (komponen BM25 krusial)
  • Latensi p95: 180ms query Qdrant + 80ms embedding = 260ms total retrieval

Guardrail Ketat untuk Kepatuhan Kebijakan

Halusinasi LLM tidak dapat diterima di customer support. Agen tidak boleh mengarang jumlah refund, deadline retur, atau biaya pengiriman.

Sistem guardrail tiga lapis:

  1. Pembatasan prompt: System prompt eksplisit melarang mengarang angka. "Jika informasi tidak ada di konteks yang diambil, respon: 'Maaf, saya perlu konfirmasi dengan tim untuk informasi ini. Bisa hubungi CS kami di...'"
  2. Validasi output terstruktur: Skema Pydantic memaksa output JSON, menolak teks bebas. Response harus include source_article_ids: list[str] untuk auditabilitas.
  3. Fact checking pasca-generasi: Regex ekstrak semua angka/tanggal dari response, verifikasi tiap item muncul di konteks yang diambil. Tolak response jika ada ketidakcocokan.
Implementasi Guardrail (Pydantic + Claude API)
from pydantic import BaseModel, Field, validator
import anthropic
import re

class SupportResponse(BaseModel):
    answer: str = Field(..., max_length=500)
    confidence: float = Field(..., ge=0.0, le=1.0)
    source_article_ids: list[str] = Field(..., min_items=1, max_items=5)
    requires_human_escalation: bool
    
    @validator('answer')
    def no_hallucinated_numbers(cls, v, values):
        # Ekstrak semua angka/tanggal dari answer
        numbers_in_answer = re.findall(r'\d+[\d.,]*', v)
        # ponytail: fact-check penuh butuh retrieved_context dari outer scope
        # Untuk sementara, flag pola mencurigakan (misal harga eksak)
        if re.search(r'Rp\s*\d{1,3}(\.\d{3})+', v):
            raise ValueError("Diduga harga halusinasi—verifikasi dengan konteks retrieval")
        return v

def generate_response(query: str, retrieved_docs: list[str]) -> SupportResponse:
    client = anthropic.Anthropic(api_key=os.getenv("ANTHROPIC_API_KEY"))
    
    context = "\n\n".join(retrieved_docs)
    prompt = f"""
{context}


Query pelanggan: {query}

Respon dalam bahasa Indonesia. Gunakan HANYA informasi dari . Jika konteks tidak mengandung jawaban, set requires_human_escalation=true. Include source_article_ids untuk auditabilitas."""
    
    response = client.messages.create(
        model="claude-sonnet-4-20241022",
        max_tokens=1024,
        temperature=0.0,  # Deterministik untuk support
        tools=[{"name": "respond", "input_schema": SupportResponse.model_json_schema()}],
        messages=[{"role": "user", "content": prompt}]
    )
    
    tool_use = next(block for block in response.content if block.type == "tool_use")
    return SupportResponse(**tool_use.input)  # Validasi Pydantic jalan di sini

# Penggunaan produksi dengan retry pada kegagalan validasi
for attempt in range(3):

        break
    except ValidationError as e:
        if attempt == 2:
            response = SupportResponse(
                answer="Maaf, sistem sedang mengalami kendala. Hubungi CS kami di +62-21-1234-5678",

Arsitektur Sistem Produksi

Infrastruktur berjalan di AWS region Jakarta (ap-southeast-3) untuk latensi rendah ke pengguna Indonesia:

  • Ingestion: Webhook WhatsApp Business API → AWS Lambda → SQS queue (pisahkan lonjakan)
  • Processing: Container ECS Fargate (Python FastAPI), autoscale 5-20 instance berdasar kedalaman SQS
  • Retrieval: Qdrant Cloud (managed, cluster 4-node, 32GB RAM/node, ~2M vektor)
  • LLM: API Claude Anthropic (Sonnet 4), fallback ke Claude Haiku jika kuota Sonnet habis
  • Monitoring: Metrik CloudWatch, dashboard Grafana, alert PagerDuty pada latensi p95 >3s atau error rate >2%

Breakdown biaya (per 1.000 query):

  • API Embedding (OpenAI ada-002): $0,01 (rata-rata 100 token/query)
  • Retrieval Qdrant: $0,02 (managed hosting teramortisasi)
  • Generasi LLM (Claude Sonnet): $0,45 (rata-rata 150 token input, 200 token output)
  • Komputasi AWS (Fargate): $0,03
  • Total: $0,51 per 1.000 query = $25,50/hari untuk 50K query

Dibanding mempekerjakan 3 agen CS tambahan @ Rp 6 juta/bulan (Rp 18 juta = ~$1.200/bulan), sistem AI biaya $765/bulan. Periode payback: 1,6 bulan.

Troubleshooting Masalah Produksi Umum

Masalah 1: Timeout Qdrant saat lonjakan traffic (burst 500 req/s)

Gejala: Latensi p95 melonjak ke 8+ detik, beberapa request timeout di 10s.

Root cause: Pool koneksi HTTP tunggal habis (default 10 koneksi).

Fix: Naikkan pool koneksi client Qdrant ke 50, tambah cache Redis untuk top 1000 query sering (78% cache hit rate), implementasi request coalescing (deduplikasi query konkuren identik).

Masalah 2: Normalisasi bahasa gaul melewatkan singkatan viral baru

Gejala: Akurasi intent turun dari 94% → 89% dalam 2 minggu.

Root cause: Tren TikTok perkenalkan slang baru ("pap" = kirim foto, "spill" = ceritakan) tidak ada di dictionary.

Fix: Review mingguan tim CS terhadap query confidence rendah (<0,6), crowdsource entri slang baru, scraping Twitter otomatis untuk hashtag trending Indonesia → review manusia → update dictionary. Akurasi pulih ke 93,5% dalam 3 hari.

Masalah 3: Rate limit API Claude terpukul saat flash sale promo (lonjakan 2000 req/s)

Gejala: Error 429, pelanggan lihat pesan fallback "Sistem sibuk".

Fix: Implementasi exponential backoff retry (hingga 3 percobaan), batching request jika memungkinkan, pre-cache jawaban untuk top 50 pertanyaan FAQ ("Cara tracking paket?", "Metode pembayaran apa saja?"), fallback ke Claude Haiku (10x lebih murah, 2x lebih cepat, kualitas acceptable untuk query sederhana). Pasca-mitigasi: error 429 turun dari 12% → 0,3% saat flash sale.

Keterbatasan dan Pekerjaan Masa Depan

Sistem saat ini tidak dapat menangani:

  • Homonim dengan konteks regional: "kok" Jawa (kenapa) vs "kok" Jakarta (terkejut negatif) — butuh deteksi dialek dari profil user/kode area (TODO)
  • Query multimodal: Pelanggan kirim screenshot pesan error — butuh OCR + vision model (evaluasi GPT-4V vs Claude Sonnet with vision)
  • Negosiasi multi-turn kompleks: Kasus refund/komplain yang butuh empati manusia — agen flag untuk eskalasi (8,2% query)

Peningkatan yang direncanakan Q1 2027:

  • Fine-tune embedding IndoBERT pada korpus customer support (kurangi ketergantungan OpenAI, potong biaya 60%)
  • Tambah input suara via voice note WhatsApp (Whisper API untuk transkripsi → pipeline existing)
  • A/B test Claude Opus untuk query kompleks (hipotesis: kurangi escalation rate 8,2% → 5%)

Poin Kunci

  1. Preprocessing deterministik mengalahkan fine-tuning model untuk bahasa gaul Indonesia (lebih cepat deploy, lebih mudah maintain, transparan untuk debugging).
  2. Retrieval hybrid tidak bisa ditawar untuk customer support (exact match nomor order butuh BM25, pemahaman semantik butuh embedding).
  3. Guardrail harus multi-lapis (prompt engineering saja tidak cukup, tambah validasi output terstruktur + fact checking pasca-generasi).
  4. Cache agresif (78% query pelanggan mengulang pola umum, Redis hemat 80% biaya API embedding).
  5. Rencanakan kegagalan API model (rate limit 429 saat lonjakan traffic, implementasi backoff + model fallback + cache FAQ).
