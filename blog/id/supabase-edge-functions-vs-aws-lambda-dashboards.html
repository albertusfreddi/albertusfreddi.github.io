Mengapa Kami Memilih Supabase Edge Functions Dibanding AWS Lambda untuk Dashboard Real-Time

16 menit • 2026-09-26

Konteks produksi: Ini adalah jalur baca di balik dashboard eksekutif untuk sebuah perusahaan distribusi Indonesia. Lima belas layar memanggil satu API untuk status pengiriman last-mile, throughput gudang, dan total invoice terbuka, yang disegarkan beberapa kali dalam satu jam oleh tim sales operations. Stack lama adalah Node.js di AWS Lambda di belakang API Gateway, dengan database di dalam VPC. Rata-rata butuh 450ms per permintaan dari Jakarta, kadang lebih dari satu detik ketika cold start menumpuk di atas reconnect database. Kami memindahkan jalur bacanya ke Supabase Edge Functions, dan layar yang sama sekarang kembali dalam 42ms pada p95. Ini perbandingan engineering yang jujur dari keduanya, bagian yang benar-benar menentukan latensi, dan satu hal di masing-masing sisi yang akan membuat kami pindah balik.

Perbedaan Cold Start Itu Nyata, tapi Itu Baru Separuh Cerita

Angka yang selalu dikutip soal serverless adalah waktu cold start. Klaim yang layak dibongkar bukanlah "Lambda lambat", melainkan "dari mana sebenarnya latensi itu datang, dan sebab mana yang dihapus oleh edge function". Sebuah permintaan Node.js Lambda yang menyentuh database VPC menghabiskan waktunya untuk beberapa hal berbeda: microVM menyala, runtime menginisialisasi, lalu kode membuka koneksi database baru, lalu query, lalu respons. Cold start hanya dua hal yang pertama.

Edge function menghapus sebagian besar start container karena ia tidak berjalan di dalam container sama sekali. Ia berjalan di isolate di dalam proses yang hidup lama, alasan yang sama kenapa tab browser bisa membuka web worker dalam milidetik. Isolate V8 diinisialisasi dari snapshot yang sudah dihangatkan, dan pada beban kami ia praktis tidak menambahkan apa pun yang terukur ke permintaan. Reconnect database, yang diam-diam adalah separuh dari latensi lama kami, adalah masalah terpisah dengan perbaikannya sendiri, dan saya bahas di bawah, karena pindah runtime saja tidak menyembuhkannya.

Kerangka yang jujur bukanlah "isolate mengalahkan container". Melainkan bahwa stack lama kami membayar tiga pajak, dan migrasi menghapus dua secara langsung dan membiarkan kami menghapus yang ketiga dengan pooler. Angka latensi di judul tidak berubah karena sihir; ia berubah karena kami berhenti membayar pajak yang sudah lama kami bayar tanpa tahu koin yang mana itu.

Isolate V8 vs MicroVM Terkontainer, dalam Konteks Waktu

Ketika permintaan tiba di Lambda, platform bisa menyimpan instance hangat, atau ia harus menempatkan permintaan di yang baru. Instance baru berarti microVM yang menyalakan kernel, memulai runtime, membaca handler-mu, dan baru menjalankannya. Angka tipikal untuk Node.js Lambda di luar VPC adalah ratusan milidetik; di dalam VPC sering lebih dari satu detik karena antarmuka jaringan elastis harus terpasang sebelum apa pun terjadi.

Isolate edge function tidak menyalakan kernel dan tidak memasang antarmuka jaringan saat permintaan datang. Mereka irisan dari proses yang sedang berjalan. Efek terukur yang kami lihat adalah variabilitas antar permintaan runtuh. Di mana stack lama punya lantai menyenangkan 120ms dan lonjakan sesekali 1,4 detik, edge function duduk di pita sempit antara 30ms dan 60ms. Untuk dashboard yang dilirik orang belasan kali sehari, lonjakan itulah yang mengikis kepercayaan jauh lebih banyak daripada rata-rata, karena rata-rata menyembunyikan momen persis saat pengguna sedang menunggu.

Edge function menang di latensi dan kesederhanaan deploy; Lambda menang di kematangan ekosistem dan di menjalankan binary native yang sewenang-wenang ketika beban kerja benar-benar membutuhkannya. Untuk dashboard yang berat di baca dan hanya bicara ke Postgres, tidak ada kekuatan Lambda yang relevan dan semua pajaknya relevan.

Jalur Query yang Benar-Benar Kami Pasang

Fungsinya tipis secara sengaja. Ia menerima JSON Web Token dari klien, memvalidasinya, memakainya untuk bicara ke Postgres dengan row-level security sehingga data pelanggan ditegakkan oleh database alih-alih oleh kode kami, dan mengembalikan baris KPI. Seluruh handler di bawah empat puluh baris karena platform yang mengerjakan pekerjaan yang kritis keamanan.

Endpoint baca dashboard
Deno.serve(async (req) => {
  const authHeader = req.headers.get("Authorization");
  if (!authHeader) {
    return new Response(JSON.stringify({ error: "missing token" }),
      { status: 401,
        headers: { "Content-Type": "application/json" } });
  }

  const supabase = createClient(
    Deno.env.get("SUPABASE_URL"),
    Deno.env.get("SUPABASE_ANON_KEY"),
    { global: { headers: { Authorization: authHeader } } }
  );

  const { data, error } = await supabase
    .from("executive_kpis")
    .select("metric_key, metric_value, updated_at")
    .order("updated_at", { ascending: false })
    .limit(20);

  if (error) {
    return new Response(JSON.stringify({ error: error.message }),
      { status: 500,
        headers: { "Content-Type": "application/json" } });
  }

  return new Response(JSON.stringify(data), {
    headers: {
      "Content-Type": "application/json",
      "Cache-Control": "s-maxage=30",
    },
  });
});

Tiga baris mengerjakan lebih banyak dari yang terlihat. Opsi global.headers meneruskan token pemanggil ke koneksi Postgres sebagai konteks permintaan, yang membuat row-level security bekerja. Header s-maxage=30 mengalihkan baca berulang ke cache edge, sehingga dashboard lima belas layar yang menyegarkan di menit yang sama tidak menjalankan ulang query yang sama lima belas kali. Dan panggilan Deno.env.get membaca secret yang tersimpan di proyek, tidak pernah di source, sehingga paket deploy tidak memuat kredensial apa pun.

Row-Level Security Memindahkan Batas Akses ke Dalam Database

Lambda lama punya lapisan otorisasi panjang yang ditulis tangan, yang memeriksa, per query, apakah pemanggil milik org distributor yang benar. Itu sumber bug justru karena ia harus diingat di setiap handler. Edge function menghapus seluruh lapisan itu dengan membiarkan Postgres menegakkannya.

RLS mengikat setiap baris ke org pemanggil secara otomatis
ALTER TABLE executive_kpis ENABLE ROW LEVEL SECURITY;

CREATE POLICY org_read
  ON executive_kpis
  FOR SELECT
  TO authenticated
  USING (org_id = (auth.jwt() ->> 'org_id')::uuid);

Yang dibeli bukan cuma kode yang lebih pendek; melainkan batas yang tidak bisa dilupakan. Panggilan auth.jwt() membaca identitas pemanggil dari token yang sama yang diteruskan fungsi. Jika engineer masa depan menambah query baru dan lupa menambah cek manual, database tetap hanya mengembalikan baris milik pemanggil, karena policy-nya ada di tabel, bukan di handler. Di stack lama, cek yang terlupakan adalah kebocoran data; di yang ini, itu bukan peristiwa. Itulah jenis perubahan yang muncul di tinjauan keamanan sebagai satu kelas temuan yang hilang.

Connection Pooler Itu Perbaikan Latensi yang Sebenarnya

Ini bagian yang dilewati kebanyakan tulisan migrasi. Function serverless sendiri tidak menyelesaikan masalah koneksi database; ia bahkan bisa memperburuknya, karena setiap isolate konkuren yang membuka sesi Postgres sendiri membakar satu koneksi dan menambah handshake penuh ke ekor permintaan itu. Lambda VPC lama kami membayar sekitar 150ms waktu connect database di atas setiap cold start karena tiap instance memelihara koneksinya sendiri.

Jawaban Supabase adalah pooler mode transaksi di depan Postgres. Fungsinya membuka koneksi pooler yang ringan, bukan sesi ke database itu sendiri, dan pooler memultipleks banyak isolate ke sejumlah kecil sesi database nyata. Biaya handshake turun dari per permintaan menjadi per sesi, dan risiko menghabiskan batas koneksi Postgres yang terbatas turun mendekati nol pada volume lalu lintas dashboard.

Tangkapannya adalah transaction pooling melarang hal yang mengasumsikan sesi tahan lama, khususnya state SET dan advisory lock yang hidup melebihi satu transaksi. Jalur baca kami tidak melakukan keduanya, jadi mode transaksi tepat. Endpoint dashboard yang hanya menyeleksi baris persis beban kerja yang dibangun untuk transaction pooling, makanya kecocokannya bersih alih-alih dipaksakan.

Biaya Bukan Alasan Utamanya, tapi Tetap Turun

Kami tidak menjalankan migrasi ini untuk berhemat, dan saya mau itu jelas, karena biaya biasanya dikutip sebagai judul berita padahal itu bagian yang paling tidak menarik. Tagihan lama adalah tumpukan item kecil: permintaan API Gateway, invokasi dan durasi Lambda, endpoint VPC, jam NAT gateway, dan log CloudWatch yang tumbuh tiap bulan entah kami baca atau tidak. Tagihan baru adalah satu biaya proyek datar dengan function, database, dan pooler di dalamnya, dan itu hanya sebagian kecil dari total lama.

Penghematan yang lebih tahan lama bersifat operasional, bukan finansial. Stack lama punya enam sumber daya berbeda yang harus tetap selaras: function, IAM role-nya, layer dengan klien Postgres, konfigurasi VPC, rute API Gateway, dan grup log. Sebuah deploy menyentuh sebagian besar dan sesekali gagal di salah satunya. Edge function adalah satu file yang didorong satu perintah, dan secret serta pooler-nya dikonfigurasi sekali di proyek. Lebih sedikit bagian yang bergerak itulah penghematan sebenarnya, dan itu yang berbunga tiap bulan.

Apa yang Akan Membuat Kami Pindah Balik ke Lambda

Keputusan jujur hanya jika kita menyebut kondisi kebalikannya, jadi ini dia. Kami akan memindahkan beban kerja balik ke Lambda ketika salah satu dari tiga hal berikut benar. Pertama, beban kerja butuh binary native atau komputasi yang sangat panjang dan berat memori yang tidak muat di batas sederhana isolate; langkah processing data yang berputar ber-menit-menit miliknya container atau queue runner, bukan edge function. Kedua, beban kerja menuntut state sesi per instance yang tahan lama, yang dilarang edge function maupun transaction pooling. Ketiga, organisasi sudah menjalankan seluruh postur keamanannya di dalam AWS dan butuh semuanya di bawah satu batas audit; maka latensi marjinal adalah biaya yang lebih kecil daripada cerita kepatuhan.

Tidak satu pun yang benar untuk jalur baca dashboard. Itulah pelajaran sesungguhnya: jawaban yang benar bukan "edge function lebih baik". Jawaban yang benar adalah "cocokkan pajak runtime dengan beban kerja, lalu perbaiki pajak koneksi database secara terpisah, karena tidak ada pilihan runtime yang menghapusnya sendirian". Kebanyakan tim yang tidak puas dengan latensi serverless sebenarnya tidak puas dengan runtime-nya; mereka tidak puas dengan reconnect database yang tidak pernah mereka ukur, dan mereka tinggal satu pooler dari angka yang jauh lebih baik.

Mengukur Migrasi supaya Angkanya Berarti

Kami juga tidak memercayai klaim di judul. Sebelum memotong, kami merekam distribusi latensi endpoint lama selama seminggu, dan setelah cutover kami merekam yang baru selama seminggu, dan perbandingannya apa adanya alih-alih apa yang dijanjikan benchmark vendor.

Disiplin pengukuran lebih penting daripada angka spesifiknya. Kami mengambil sampel bukan hanya mean tetapi seluruh ekor, karena kelambatan yang dirasakan dashboard hidup di ekor, dan kami mengukur dari probe di Jakarta terhadap URL produksi alih-alih dari shell di region yang sama. Jika kamu mau mengklaim perbaikan latensi, ukur end to end, dari tempat yang sama tempat penggunamu benar-benar duduk, dan rekam distribusinya, bukan satu tarikan yang beruntung.

Probe endpoint live yang sadar ekor
import asyncio
import httpx
import statistics

async def sample(url, n=200, token=None):
    headers = {"Authorization": "Bearer " + token} if token else {}
    async with httpx.AsyncClient() as client:
        times = []
        for _ in range(n):
            start = asyncio.get_event_loop().time()
            await client.get(url, headers=headers)
            times.append(asyncio.get_event_loop().time() - start)
    times.sort()
    return {
        "p50_ms": round(times[len(times)//2] * 1000, 1),
        "p95_ms": round(times[int(len(times)*0.95)] * 1000, 1),
        "max_ms": round(max(times) * 1000, 1),
    }

Probe-nya sengaja tumpul: permintaan HTTP nyata dengan header auth nyata, tanpa pemanasan yang memalsukan kasus terbaik. p95 yang dicetaknya adalah angka yang kami kutip, karena p95 adalah latensi tertinggi yang dialami pengguna sebelum mereka menyentuh ekor yang sial, dan itu jauh lebih berarti bagi pemilik produk daripada rata-rata yang tidak dirasakan siapa pun.

Apa yang Akan Kami Pakai Ulang dan yang Tidak

Kami akan memakai ulang tiga keputusan tanpa mengubahnya: pola handler tipis yang mendorong policy akses ke dalam database lewat row-level security, pooler mode transaksi, dan cache edge s-maxage yang meruntuhkan baca berulang. Tiga hal itulah yang sesungguhnya memikul angka latensi. Kami tidak akan menciptakan ulang jalur tulis dashboard di edge function, karena tulis butuh logika idempotensi dan kadang transaksi lebih panjang yang tidak dioptimalkan untuk model itu, dan kami tidak akan migrasi sekaligus; memotong satu layar baca pada satu waktu memberi kami radius ledakan kecil dan perbandingan jam ke jam alih-alih pertukaran besar sekaligus. Pelajaran tahan lamanya singkat: latensi serverless biasanya dua pajak dalam satu jas hujan, dan kamu hanya bisa menghapus pajak runtime setelah mengukur pajak database.
