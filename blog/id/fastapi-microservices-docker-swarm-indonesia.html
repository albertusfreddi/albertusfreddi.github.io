Deploy Microservices FastAPI Ringan Menggunakan Docker Swarm di Cloud Lokal

16 menit • 2026-10-05

Konteks produksi: Sebuah startup logistik di Jakarta menjalankan delapan layanan backend di tiga instance VPS kecil, tanpa load balancer dan deploy dilakukan manual lewat SSH. Kami menggabungkannya ke satu kluster Docker Swarm di kumpulan node cloud lokal seharga $40 per bulan, menambahkan Traefik untuk routing dan TLS otomatis, lalu mencapai deploy bergulir tanpa downtime tanpa menyentuh Kubernetes. Waktu deploy turun dari 40 menit langkah manual menjadi satu docker stack deploy, dan tim berhenti membayar sumber daya menganggur yang tidak terpakai.

Kubernetes adalah Alat yang Benar untuk Masalah yang Tidak Dimiliki Kebanyakan Startup

Kubernetes memecahkan masalah nyata: menjalankan ribuan workload di ratusan node, dengan penjadwalan, kebijakan, dan multi-tenancy yang halus. Ia juga, dalam hitungan jujur apa pun, berat. Control plane saja ingin minimal tiga node, etcd adalah disiplin operasional tersendiri, dan model objeknya cukup dalam sehingga tim kecil menghabiskan berminggu-minggu mempelajari apa yang sebenarnya dilakukan Deployment, ReplicaSet, dan StatefulSet sebelum mengirim apa pun.

Wawasan kuncinya: kebutuhan orkestrasi tumbuh seiring jumlah perhatian yang berbeda di sistem Anda, bukan seiring angka microservices yang Anda baca di blog. Delapan layanan, satu database, satu antrean, beberapa worker latar, dan satu operator bukanlah masalah Kubernetes. Ia adalah masalah Swarm, dan Swarm dirancang persis untuk rentang itu.

Mengapa Docker Swarm, Secara Khusus

Nilai Swarm bukan karena ia kuat. Melainkan karena ia proporsional. Ia memakai ulang konsep Docker yang sudah dikenal tim, image dan network dan volume, dan hanya menambah sedikit: service (keadaan yang diinginkan dari N replika), stack (file YAML yang menggambarkan banyak service), dan overlay network yang membuat kontainer bisa berbicara lintas host. Itu hampir seluruh permukaan API yang harus dipegang kepala tim kecil.

Alasan kedua bersifat operasional. Swarm tidak butuh control plane terpisah yang Anda rawat; peran manager berjalan di salah satu node yang sudah ada, dengan replika yang dipilih otomatis. Untuk sistem delapan service, tiga manager adalah keseluruhan "platform"-nya, dan ia menurun dengan anggun ke kuorum dua manager saat pemeliharaan. Bandingkan dengan mendirikan etcd, scheduler, API server, dan controller-manager, masing-masing dengan log dan cara gagalnya sendiri.

docker-stack.yml — seluruh deskripsi sistem tingkat atas
version: "3.8"

services:
  api:
    image: registry.example.id/logistics-api:2.4.0
    deploy:
      replicas: 4
      update_config:
        parallelism: 1
        order: start-first
        failure_action: rollback
      restart_policy:
        condition: on-failure
    networks:
      - overlay

  worker:
    image: registry.example.id/logistics-worker:2.4.0
    deploy:
      replicas: 2
      restart_policy:
        condition: any
    networks:
      - overlay

  traefik:
    image: traefik:v2.11
    command:
      - "--providers.docker.swarmMode=true"
      - "--providers.docker.exposedByDefault=false"
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock:ro
    deploy:
      placement:
        constraints:
          - node.role == manager
    networks:
      - overlay

networks:
  overlay:
    driver: overlay

Perhatikan apa yang tidak ada di sini: tidak ada spec pod, tidak ada service account, tidak ada kuota sumber daya, tidak ada namespace. Itu intinya. File ini menggambarkan sistem yang benar-benar dijalankan bisnis ini, tidak lebih, dan siapa pun di tim bisa membacanya dari awal sampai akhir dalam semenit.

Routing dan TLS dengan Traefik, Bukan Nginx Rakitan Tangan

Kesalahan paling umum yang kami lihat di deploy kecil adalah memelihara konfigurasi Nginx manual yang memetakan nama host ke IP upstream. Begitu replika pindah atau IP berubah, konfigurasi itu berbohong kepada Anda, dan outage datang dari bagian yang tadinya tampak paling sederhana. Provider Swarm Traefik membaca Docker API secara langsung: ia menemukan replika sehat secara otomatis dan memuat aturan routing dari label pada service itu sendiri.

label pada service api — routing dideklarasikan di sebelah aplikasi
  api:
    image: registry.example.id/logistics-api:2.4.0
    deploy:
      labels:
        - "traefik.enable=true"
        - "traefik.http.routers.api.rule=Host(`api.logistik.id`)"
        - "traefik.http.routers.api.tls.certresolver=letsencrypt"
        - "traefik.http.services.api.loadbalancer.healthcheck.path=/healthz"
      replicas: 4
      restart_policy:
        condition: on-failure

(Pada YAML stack sungguhan, aturan host ditulis Host(`api.logistik.id`); host di atas ditampilkan secara konseptual agar tidak membingungkan kode blok.) Path health-check memberi makan load balancer Traefik, sehingga replika yang mulai mengembalikan 500 otomatis dikuras dari pool alih-alih ikut memikul traffic produksi. Label tunggal itu lebih berharga daripada daftar upstream statis mana pun, karena ia tidak akan pernah melenceng dari service yang digambarkannya.

Sisi FastAPI: Stateless, Terperiksa Kesehatan, dan Horizontal

Agar microservices benar-benar bisa skala horizontal, mereka harus mematuhi satu aturan: sebuah request bisa mendarat di replika mana pun dan menghasilkan hasil yang sama. Artinya tidak ada session dalam memori yang tidak ikut dibagikan, tidak ada file lokal server yang diandalkan request berikutnya, dan tidak ada state di proses yang berarti melampaui satu request. FastAPI memudahkan menegakkan ini karena framework menjaga semuanya eksplisit: dependency dirakit per request, dan apa pun yang punya siklus hidup lewat konteks lifespan.

main.py — titik masuk service yang tangguh dan terperiksa
from contextlib import asynccontextmanager
from fastapi import FastAPI

@asynccontextmanager
async def lifespan(app: FastAPI):
    # Buka koneksi bersama (pool Postgres, klien pesan) di sini.
    app.state.pool = await create_pool()
    yield
    await app.state.pool.close()

app = FastAPI(lifespan=lifespan)

@app.get("/healthz")
async def healthz():
    # Liveness: proses hidup. Readiness memeriksa dependensi di bawah.
    return {"status": "ok"}

@app.get("/readyz")
async def readyz():
    # Readiness: bisakah replika ini sungguh melayani?
    db_ok = await ping_database(app.state.pool)
    if not db_ok:
        return JSONResponse({"status": "unready"}, status_code=503)
    return {"status": "ready"}

Pemisahan antara /healthz dan /readyz bukan pedantri. Liveness memberi tahu Docker apakah harus me-restart kontainer; readiness memberi tahu load balancer apakah harus mengirim traffic. Kalau database mati dan Anda hanya punya liveness, setiap replika di-restart dalam lingkaran sementara masalah sebenarnya, database, tidak ke mana-mana. Dengan readiness, replika tetap jalan, berhenti menerima traffic, dan outage terisolasi sampai dependensinya pulih.

Deploy Bergulir yang Tidak Menjatuhkan Satu Request Pun

Alasan utama repot-repot memakai orkestrasi adalah untuk deploy tanpa menjatuhkan traffic. update_config Swarm memberi tiga tuas yang bersama-sama membuat deploy bergulir aman: parallelism mengontrol berapa replika berubah sekaligus, order: start-first berarti kontainer baru mulai dan lolos health check sebelum yang lama berhenti, dan failure_action: rollback berarti deploy gagal mengembalikan Anda ke titik awal alih-alih meninggalkan Anda dalam keadaan setengah naik.

skrip deploy — build sekali, promosikan berdasarkan digest
#!/usr/bin/env bash
set -euo pipefail

SERVICE="$1"
TAG="$2"
REGISTRY="registry.example.id"

# Build sekali dan tag secara immutable, agar deploy mempromosikan digest pasti.
docker build -t "$REGISTRY/$SERVICE:$TAG" "./services/$SERVICE"
docker push "$REGISTRY/$SERVICE:$TAG"

# Perbarui hanya service itu di dalam stack yang sedang berjalan.
docker service update "$SERVICE" \
  --image "$REGISTRY/$SERVICE:$TAG" \
  --update-parallelism 1 \
  --update-order start-first \
  --update-failure-action rollback \
  --with-registry-auth

Dua kebiasaan penting di sini. Pertama, Anda build dan push image dengan tag unik, lalu mempromosikan image persis itu ke dalam stack; Anda tidak pernah mengandalkan tag latest yang bisa berubah, karena "latest" hari Senin bukan "latest" hari Selasa dan rollback butuh target pasti. Kedua, deploy memperbarui satu service, bukan seluruh stack, yang menjaga radius ledakan tetap pada hal yang benar-benar Anda ubah dan membuat rollback sepele.

Tata Letak: Mengajari Swarm Tempat Segalanya Harus Berjalan

Di kluster sekecil tiga node Anda mungkin tidak butuh placement constraint sama sekali, tapi ada dua hal yang layak dipancang. Peran manager sebaiknya dijauhkan dari traffic worker terpanas, dan hal yang stateful (database, antrean) harus punya perilaku restart dan update yang tidak menganggapnya dapat dibuang seperti API stateless.

WorkloadReplikaKebijakan restartPlacement constraint
API (stateless)4on-failureworker mana pun
Worker (latar)2anyworker mana pun
PostgreSQL1any + mountpancang ke node pemegang volume
Traefik1anynode.role == manager

Database adalah satu baris yang menuntut kehati-hatian. Di Swarm Anda memancang service stateful ke node yang memiliki named volume mereka, karena kontainer database yang mengambang antar-node sementara datanya tertinggal adalah bencana bertahap. Saat Anda tumbuh melampaui satu node, itu sinyal untuk memindahkan database ke layanan terkelola atau host khusus, bukan melawan scheduler Swarm dengan constraint yang makin kreatif.

Mode Kegagalan yang Benar-Benar Kami Tembus

Masing-masing adalah kesalahan yang kami buat di produksi dan masing-masing punya bentuk yang sama: kegagalan datang dari membiarkan default yang mengasumsikan hal yang salah. Liveness mengasumsikan proses hidup berarti bisa melayani; latest mengasumsikan tag stabil; volume yang tidak dipancang mengasumsikan penyimpanan ikut kontainer. Disiplin orkestrasi sebagian besar adalah disiplin untuk tidak membiarkan asumsi tak terperiksa, dan Swarm memunculkan asumsi itu cukup jelas sehingga tim kecil benar-benar bisa mengimbanginya.

Saat Swarm Berhenti Cukup

Swarm adalah jawaban yang tepat untuk rentang di mana Anda punya segelintir service, segelintir node, dan satu tim yang menguasai semuanya. Pemicu jujur untuk pindah ke Kubernetes bukanlah "kami baca itu standar industri." Melainkan hal-hal seperti: Anda butuh GitOps dan kebijakan yang dituntut organisasi banyak tim; Anda butuh autoscaling yang menolak didekati dengan jumlah replika manual; Anda butuh ratusan node dan scheduler harus membuat keputusan penempatan yang tidak bisa dibuat manusia. Sampai salah satunya benar, Swarm akan membawa Anda lebih jauh daripada reputasinya, dan uang serta perhatian yang Anda hemat bisa masuk ke aplikasi, tempat bisnis yang sesungguhnya hidup.
